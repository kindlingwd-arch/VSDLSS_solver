# 求解加速策略清单：讨论过的思路与结论（2026-10-19）

2026-10-17 至 10-19 讨论和实测过的所有求解加速思路，每条注明是否有效和依据，方便以后遇到新方法时先查这里。

设计方案和数学原理见 [transient-stepping-design-20261018](transient-stepping-design-20261018.md)，流水线实验见 [solve-overlap-pipeline-20261017](solve-overlap-pipeline-20261017.md)，参考文献见 [docs/references](../references/README.md)。

## 0. 先用这个问题筛一遍

线上 6100 万结点双网用例，32 线程，每步约 165 ms：收集 34、前代回放 40、core 20–28、回代回放 32、写回 28（ms）。求解受内存带宽限制，每步时间约等于"要读的数据量 ÷ 实际带宽"。所以一个新方法要有明显收益，必须满足下面至少一条：

1. 减少每步要读的字节数；
2. 减少读的次数（同一份数据少从内存读几遍）；
3. 减少求解的次数（时间步数）；
4. 提高实际可用的带宽（例如 NUMA）。

只解决计算慢、并行度不够、同步太多的方法，在这里大多只有几个百分点的收益。

结论标记：**有效**：已实测有收益；**待测**：有依据，等服务器数据；**主方案**：已设计，待实施；**已具备**：现有代码已实现；**无效**：实测或分析无收益；**不适用**：前提不成立。

## 1. 已具备（现有代码已实现）

| 思路 | 现有实现 |
|---|---|
| 超节点、按块存储因子，求解用二级 BLAS（MA32 → MA42 的演进） | core 面板连续存放（压缩三角块 + 外部行块）；宽面板用 `dtpsv` + `dgemv`，窄面板用 AVX2 内核 |
| 无屏障自调度（原子入度计数） | 树顶前代每个面板有"未完成子结点"计数器；回代按分支用任务调度；尾部窗口调度只有一次屏障 |
| 前代改成目标拉取、无锁并行 | 树顶前代为拉取形式，各线程写的区域互不重叠，没有锁或原子写 |
| 大面板拆给多个线程 | 不用 BLAS 时已实现（`forward_pull_par`）；用 BLAS 时树顶主干单线程（见第 3 节） |
| 32 位索引 | core 下标 `int32_t`；消元记录邻居 `uint32_t`，重编号后主元位置不存，度数 1 字节 |
| 批处理、内存级并行度 | 每条记录只有几条指令，乱序执行窗口自动重叠十几条记录的取数；32 个线程各自并行 |
| 收集、写回的访存优化 | 两遍分桶重排加流式存储 |
| 低度消元（链、悬挂树一步收缩） | 度数 ≤3 的结点逐个消元，等价于树收缩 |
| 商图 AMD、超节点数值分解 | ordering 5（商图 AMD）、ordering 6（METIS）；core 超节点分解加 BLAS |
| 编译器优化 | 关键内核按运行时检测使用 AVX2，不依赖 `-march` |

## 2. 无效或不适用

| 思路 | 依据 | 结论 |
|---|---|---|
| 回代侧数据流流水线（`VSDLSS_PIPE_BWD=1`） | 服务器实测 core + 回代 48 → 46 ms/网 | 无效（约 1%），保留为默认关闭的开关 |
| 前代侧流水线 | 模型 −5 ms/网，按回代侧的实测折算只剩一半左右，实现更复杂 | 不做 |
| 用接口响应 H 解耦回放与 core | 4 核实测慢 66%；服务器估算每网净慢约 14 ms | 无效 |
| 仿射前缀扫描 | 依赖深度（尾部约 340 层，每层约 9.5 万条）不是瓶颈；运算和访存多约 2 倍 | 无效（只适合 GPU） |
| 串联链一步投影（α、β 分压系数） | 链内的局部解每步随 b 变化，仍要递推；读的字节不减少 | 无效 |
| 邻居下标压缩到 16 位、相邻记录（`nb_stats`） | 邻居是下一条记录的比例约 0%；16 位以内 23–62%；字节只少 2–7% | 无效 |
| 对角块显式求逆 | 分支 `perf/selinv-20260928` 实测：整次求解最多快 1.3%，准备开销约 530 步才收回；对角块占 L 约 17%，逆的存储量不变 | 无效 |
| 分块逆、团树重排（Alvarado、Pothen、Peyton） | 无填充的逆因子与 L 的非零元一样多，读的字节不变；串行深度不是瓶颈 | 无效 |
| 按度数分组凑成矩阵乘法 | 每个乘子每次求解只用一次，本质是稀疏乘向量，读的字节和运算之比不变；还要按依赖分层同步 | 无效 |
| 跨记录的 SIMD 向量化 | 同一连通块内的记录有依赖；度数不同；AVX2 没有 scatter | 无效 |
| 稀疏右端项、零子树剪枝 | 实测 b 中只有约 20% 为零，汇集到 core 后基本全部非零 | 不适用 |
| 结构零预处理（恒为 0 的结点） | 最多影响前代的 20%，约 1–4% | 收益太小，不做 |
| 只求部分结点的解 | 每步需要全部结点的电压，而且 $\frac{C}{h}x_k$ 需要完整的解 | 不适用 |
| 分解时同步做前代（融合分解与求解） | 只省第一次求解的一遍前代（约 50 ms/网，一次性）；回代方向相反，省不掉 | 无效 |
| `-O3 -march=native` | 本机实测无差别 | 无效（不需要） |
| `-ffast-math` | 会删掉约 80 处 `isfinite` 检查，破坏逐位一致 | 禁止 |
| 多线程排序（mt-metis、ParMETIS） | 只影响分解时的排序；ParMETIS 排序质量更差，会让每步求解变慢 | 等分解分项计时后再定 |
| 从零重写求解器 | 直接法的下限都是"读两遍因子"，重写读的数据量差不多 | 不做 |
| 改用迭代法 | 低度消元后填充很少，因子和 A 差不多大；迭代超过 1 次就比现在慢 | 不做 |
| 多右端项 | 已决定不考虑 | 跳过 |
| 主动驱逐用完的数据（`clflushopt` 等） | GB 级数据逐行驱逐开销大；与跨步融合"希望数据留在缓存"的方向相反 | 低优先级 |
| 多核之间的脏行传递（`clwb` 等） | 各并行阶段写的区域互不重叠，跨核读脏行只发生在阶段交接，数据量小 | 不适用 |

## 3. 待测（有依据，等服务器数据）

| 思路 | 已有证据 | 预计收益 | 工具 |
|---|---|---|---|
| NUMA 交错分布（`VSDLSS_INTERLEAVE=1`） | **已实测有效**（[numa-placement-20261019](numa-placement-20261019.md)）：每步 563 → 151 ms。主因是避开了内核自动 NUMA 平衡造成的缺页（每步约 61 万次 → 约 300 次） | 约 3.7 倍，不用改代码 | 立即采用；下一步在库内对大块内存自动设置交错策略 |
| NUMA 按使用者放置数据（静态映射） | 交错分布后仍有约一半访存是远程的 | 在交错分布基础上可能再快一些，幅度未知 | 库内交错做完后再评估 |
| FP32 因子（单精度存储，双精度计算） | 本机相对误差 1.4e-7（只有非对角部分用单精度）、2.3e-7（全部用单精度）；修正一步后 5.5e-12 | 每步快 15–20% | `tools/fp32_probe_test.sh` |
| 回放软件预取（`VSDLSS_PREFETCH=P`，默认关闭） | 本机：未调度的串行尾部快 19–24%；窗口调度路径上，前代在 1–2 线程时快 12–16%，4 线程时慢 12%；回代在所有线程数下都变慢 7–25% | 服务器上估计最多约 2% | `tools/ab_test.sh`；建议改为只对前代预取再测 |
| core 树顶主干拆分（用 BLAS 时主干单线程） | 本机 4 核（每网 2 线程）四种设置无差别 | 估计每网 1–3 ms | `tools/ab_test.sh` |
| 每步计算残差 $\|b-Ax\|$ 的开销 | 一次 $A\cdot x$ 的读取量和一遍回放相当；求解器内部不算，取决于仿真器是否每步算 | 如果每步都算，减少计算频率可省几十 ms | 需要确认仿真器的做法 |

## 4. 主方案（已设计，待实施）

| 思路 | 依据 | 预计收益 | 状态 |
|---|---|---|---|
| 求解器接管时间步进：全程使用内部顺序，电流源用稀疏列表 | 省掉每步的收集和仿真器组装 b | 每步约 165 → 130 ms | 前提已确认（电容接地、步长固定、电流源稀疏、每步输出全部结点）；耦合电容数量待查网表 |
| 跨时间步融合：第 k 步回代和第 k+1 步前代按连通块交错执行 | 消元记录每步只从内存读一遍；$b_{k+1}$ 在回代时顺手算出 | 约 90–100 ms | 同上 |
| 叠加 FP32 因子 | 见第 3 节 | 约 70 ms | 待精度确认 |

## 5. 更大的方向（未展开）

| 思路 | 说明 |
|---|---|
| 减少时间步数：梯形法、Gear2、指数积分器（MATEX 等） | 需要改仿真器的时间积分，潜力可能是数倍 |
| GPU 求解 | 带宽高一个数量级，但每步右端项和解要过 PCIe，必须把整个时间推进放到 GPU 上 |
| 模型降阶（PRIMA 等） | 电源网格的电流源端口太多，降阶效果通常不好 |
| ECO 增量分析时的因子更新/降秩修正 | 只改少量电导时不必重新分解；对每步求解时间没有帮助 |
