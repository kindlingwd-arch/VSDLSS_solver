日期：2026-09-12。基线 `22c3638`（`main`，已合并 `codex/parallel-supernodal`、
`codex/panel-speed-20260910`、`codex/small-kernels-20260911`、

分支 `codex/parallel-efficiency-20260912`。

本文只记录并行效率相关的改动、依据和实测；设计背景见
[08-parallel-design.md](08-parallel-design.md)，串行内核历史见
[09-panel-speed.md](09-panel-speed.md) 和 [11-small-kernels.md](11-small-kernels.md)。

## 约束

**所有改动保持逐位（bitwise）一致。** 每个输出元素的浮点运算序列与改动前
完全相同：累加仍从 `+0` 开始、仍按 `k = 0..width-1` 递增、散射顺序不变。
改动只调整“哪些值被复用、谁来执行、以什么顺序装载”，不调整“按什么顺序相加”。
新增 `test/test_kernels.c` 把改动前的逐元素内核原样复制为参考实现，
对跨越全部分块边界的尺寸做 `memcmp` 比较；原有 1/2/4 线程逐位测试全部保留。

## 诊断：瓶颈不在原先认为的地方

在 3D Poisson 网格（单连通分量，MLD 排序）上按阶段计时后，基线的实际分布是：

| 阶段 | 22³ = 10648 阶，2 线程 | 占比 |
|---|---:|---:|
| 规范化 + 分量 + 抽取 | 0.002 s | 0.1% |
| 度 0–3 缩减 | 0.002 s | 0.1% |
| MLD 排序 | 0.234 s | 12.9% |
| **符号分析 `vsdlss_sn_analyze`** | **1.290 s** | **71.1%** |
| 数值分解 `vsdlss_sn_factorize` | 0.219 s | 12.1% |

也就是说：**基线中 88% 的分解时间是完全串行的预处理**，其中符号分析一项就占 71%。
既有的并行工作全部集中在剩下的 12% 上，所以 `vsdlss_factorize_m3`
在单连通分量矩阵上的 2 线程"加速比"实测为 **0.98×（负加速）**——
多开一个线程带来的内存与调度竞争超过了它在 12% 上省下的时间。

这是本次优化的主线：先把串行部分削掉并使其可并行，再改进数值内核的访存，
最后修掉任务 DAG 的调度开销。

## 改动一：符号分析的合并扫描与分量并行（`vsdlss_supernodal_symbolic.c`）

`update_target` 的构造原本是

```c
for (q = 0; q < ext; ++q) for (r = q; r < ext; ++r)
    z->update_target[total++] = z->l_panel_slot[find_l_entry(z, R[q], R[r])];
```

即对 `sum_s |R_s|(|R_s|+1)/2` 个元素各做一次二分查找。但 `R` 与每个 L 列的
行号表都是升序存放的，所以整行查找可以退化为一个单调推进的游标：
对固定的 `col = R[q]`，`r` 递增时目标条目也只会前进。`l_panel_slot` 的
外部行定位同理。两处都从 `O(ext·log nnz)` 变成 `O(ext + nnz_col)`。

其次，这两个循环的输出切片按超节点划分（`l_panel_slot` 跟随 `l_col_ptr`、
`update_target` 跟随 `update_ptr`），互不重叠，因此可以直接对超节点做
`omp for schedule(guided)`。这里只产生整数下标，不做任何浮点运算，
并行与否不影响数值结果。

实测（22³，与上表同一矩阵）：

| | 基线 | 本分支 1 线程 | 本分支 2 线程 |
|---|---:|---:|---:|
| `vsdlss_sn_analyze` | 1.290 s | 0.696 s | 0.200 s |

合并扫描带来 1.85× 的串行加速，分量并行再带来 3.5×，合计 **6.4×**。

## 改动二：分块的外部块更新内核（`vsdlss_panel_update_range`）

基线对每个输出元素调用一次 `vsdlss_panel_dot`：

```c
for col: for row: panel[target] -= dot_k( a[k*rows + w+row] * a[k*rows + w+col] )
```

每个内积沿 `k` 以 `rows` 为步长跨越整个面板，一个输出元素要触及 `width`
条不同的缓存行，且相邻输出之间没有任何复用。这是纯访存负载：既无法向量化，
也没有可供第二个线程重叠的计算——这正是数值阶段加速比上不去的原因。

新内核保持面板布局不变，把循环翻转成在小累加瓦片上的 rank-1 更新
（`VSDLSS_PANEL_UPDATE_CB = 4` 列 × 256 行）：

```c
for k: { cv = pk[col]; for i: acc[i] += pk[r0+i] * cv; }
```

`k` 循环连续读取列片段，一次装载服务 4 个输出。每个累加器仍从 `+0` 开始、
仍按 `k` 递增累加，因此与 `vsdlss_panel_dot` 逐位一致（`test_kernels`
对 width 1–33、ext 1–300 以及整体/分块两种调用方式做了 `memcmp` 验证）。

调用方 `vsdlss_sn_factorize` 改为按列块（而非单列）做 `omp for schedule(dynamic,1)`；
列块之间目标槽互不相交，仍然没有累加竞争。

## 改动三：左视任务图（`factor_dag`）

基线的 DAG 是右视的：对每个（源超节点，目标面板块）对生成一个任务，
即装配图的每个非零块一个任务，各带两条 `depend`。任务创建和依赖解析
都要拿 team 的 task 锁，于是成千上万个微任务的调度成本远超它们携带的算术量。
`make test` 中 `test_reduced_dag` 的实测是 DAG 比串行**慢 18–26 倍**：

```
serial numeric_ms=3.050 supernodes=448
DAG threads=2 numeric_ms=54.497
DAG threads=4 numeric_ms=78.142
```

改为左视：**每个面板恰好一个任务**，该任务按源编号递增依次施加所有指向
该面板的贡献，然后分解该面板。依赖边完全相同（用 OpenMP 5.0 的
`depend(iterator(...))` 表达"等待我的全部源"），但任务对象从
"装配图非零块数"降到 `count`，且一个面板的整段左视更新成为一个可窃取的工作单元。
由于目标面板收到的贡献顺序仍是源编号递增，与串行循环完全一致，结果仍逐位相同
（`test_reduced_dag` 已有的 `memcmp` 校验覆盖这一点）。

同一台机器、同一测试：

```
serial numeric_ms=2.223 supernodes=448
DAG threads=2 numeric_ms=6.652      (基线 54.497，改善 8.2×)
DAG threads=4 numeric_ms=12.378     (基线 78.142，改善 6.3×)
```

依赖子句里的 iterator 属于 OpenMP 5.0。GCC 与 clang 在把 `_OPENMP` 提到
201811 之前很久就已支持，所以按编译器版本选择（GCC ≥ 9、clang ≥ 12）；
不支持时 `vsdlss_set_dag_enabled(1)` 直接回落到常规路径，而不是回到那个
经实测在所有尺寸上都慢于串行的右视实现。

**DAG 仍然是 opt-in，且默认关闭。** 上面的测试矩阵是自然序 512 阶网格，
消元树近乎一条链，几乎没有树级并行可言，所以即使改善 8 倍，
DAG 在该用例上仍慢于常规路径。它值得开启的场景是填充缩减排序之后、
消元树足够宽且面板足够大的矩阵。

## 改动四：三角求解的复用与多 RHS 暂存

- 前代：把一块外部目标行保留在寄存器里、沿 `j` 外扫，把步长为 `rows`
  的面板读取变成连续读取（块大小 128）。
- 回代：把 `x[index[r]]` 一次性收集到连续缓冲（≤1024 项用栈，超出用一次
  `malloc`，分配失败则走原来的逐元素回退路径），不再为 J 的每一列重新经
  `index[]` 间接寻址。
- `vsdlss_m3_solve_many`：`work` 本就是每个 RHS 私有的暂存，因此改为直接
  写入，省掉 `vsdlss_m3_solve` 内部那一层 per-RHS 暂存缓冲与 `memcpy`。

三者都保持每个元素的累加顺序，只改变复用方式。

**跨超节点的三角求解没有并行化，这是刻意的。** 前代中不同超节点会更新同一
外部行，一旦并行，累加顺序就随线程调度变化，无法满足逐位约束。
该路径可用的并行仍然只有：多 RHS 之间（`vsdlss_m3_solve_many`）
和大面板内部的外部行。

## 实测

环境：2 vCPU，GCC 13.3.0，`-O2 -Wall -Wextra -std=c11 -fopenmp`。
**只有 2 个核**，所以下面只能给出 2 线程数据；不同硬件、核数与矩阵会改变结果，
这些数字不构成对任何其他平台的性能承诺。取 1 次预热后 3 次运行的最小值。

`./bench_sn <side> 2 8`，3D Poisson 网格，单连通分量，MLD 排序：

| 单 RHS 求解 | 0.00488 s | 0.00527 s | 0.93× | 0.00475 s | 0.00512 s | 0.93× |
| 8 RHS 求解 | 0.02436 s | 0.01398 s | 1.74× | 0.02145 s | 0.01470 s | 1.46× |

### 18³（n = 5832）

| 阶段 | 基线 1 线程 | 基线 2 线程 | 基线加速比 | 本分支 1 线程 | 本分支 2 线程 | 本分支加速比 |

### 怎么读这些数字

多处“加速比”列的数值反而下降了（例如 8 RHS 从 2.23× 降到 1.57×），
因为**分母变小了**：串行路径本身快了 1.4–1.9 倍。绝对时间在每一格都不差于基线。
把加速比当作唯一指标会奖励"把串行版本写慢"，所以上表同时给出绝对时间。

分解的 2 线程加速比只从 0.98× 升到 1.13×，原因是 Amdahl：
符号分析被削掉之后，**MLD 排序成了新的串行大头**。22³ 上预处理
0.944 s（1 线程）里有 0.244 s 是排序，占 26%，且完全串行；
按 2 线程算，理论上限约 1.6×，实测 1.13× 与之相隔的部分是数值阶段
仍受访存带宽限制（这台 2 vCPU 机器上更新内核实测约 2.2–2.8 GF/s）。

## 已知剩余瓶颈（按价值排序）

1. **MLD 排序串行**（现占分解时间约 26%）。`order_connected` 的左右子集
   递归天然独立，但 `mld_context` 里的 `member`/`distance`/`queue` 是共享
   暂存，`separators` 是共享计数；并行化需要每任务一份上下文，
   且必须证明分区与 tie-break 不随执行顺序改变——否则排序结果会变，
   进而改变 `nnz(L)` 和全部下游数值。本次未做，因为风险与"逐位一致"
   约束直接冲突，应当单独立项并配确定性测试。
2. **更新内核的散射仍是访存瓶颈**。每个输出要读一个 `update_target` 并写一个
   面板槽，`sum_s |R_s|(|R_s|+1)/2` 项。经典做法是相对下标映射
   （relative index map），可以完全消去 `update_target` 数组——既省内存
   （该数组可以大于 `nnz(L)`）也省一半访存。这会改变 `vsdlss_sn_symbolic`
   的公开布局和 `test_m3` 中对它的断言，属于结构性改动。
3. **每个超节点一次 fork/join**。数值阶段对每个超过阈值的超节点新建一个
   OpenMP team。持久 team（整个超节点循环一个 `omp parallel`，
   对角块用 `single`、更新用孤立 `omp for`）可以省掉这部分开销，
   但要把 `vsdlss_panel_factor` 改造成能参与外层 team 的形式。
4. **工作量阈值 100000 是全局常数**，对符号分析、分量、面板、求解共用一个值。
   它没有按阶段的算术强度区分，也没有按机器标定。
