# 2026-10-09 单阶段求解基准 `bench_phase`

## 目的

整体求解的同进程 A/B（两个库各分解一次，再交替求解）在 16M 上要 10–15 分钟，而且在笔记本上：

- 求解各阶段都受内存带宽限制（8 线程约 13–18 GB/s），两个网同时跑时调度类改动的收益被带宽吃掉；
- 单次运行波动 30–50%，3–5% 的改进很难分辨。

`test/bench_phase.c` 只分解一次，然后**单独**计时求解的各阶段，一次扫多个线程数：

| 阶段 | 调用 |
|---|---|
| replay fwd / bwd | `vsdlss_reduce_forward_inplace` / `vsdlss_reduce_backward_inplace`，全部记录 |
| blocks fwd / bwd | 只保留并行块段（尾段置空的视图） |
| tail fwd / bwd | 只保留顺序尾段（块段置空的视图） |
| core fwd+bwd | `vsdlss_sn_solve_inplace`（核心超节点树求解） |

每项取中位数（每次重复前在计时外重置向量），并给出有效带宽（回放按记录字节，核心按 L 读两遍）；
最后检查不同线程数的结果逐位一致。

输入：

- `PG_DUMP` 文件（与 `bench_pardiso`、`bench_dump_solve` 同格式）：真实用例，只取最大的分量；
- `grid:SIDE[:CHAIN]`：SIDE×SIDE 网格，每条边是 CHAIN（默认 3）个中间节点的链，度数 2 和 4 混合，
  类似电源网。小 SIDE 时工作集在缓存内（"热"），没有内存带宽上限，用来近似高带宽服务器上
  每个核的情况，暴露调度、同步和串行开销。

```bash
make bench_phase METIS=1
./bench_phase grid:200 6 "1 2 4 8" 21        # 约 28 万节点，热，1 秒内
./bench_phase grid:700 6 "1 2 4 8" 21        # 约 340 万节点，冷，数秒
./bench_phase emir16M.bin 6 "1 2 4 8" 15     # 真实 16M，最大分量 832 万节点，约 3 分钟
```

不覆盖：收集/写回（见 `bench_perm2_only`、`bench_perm3`）、单面板内核（见 `bench_panel_kv`）、
两个网并发时的带宽竞争（仍需整体 A/B）。

## 首次使用：顺序尾段的层调度（分支 `perf/tail-levels`，未合入）

改动：把低度消元顺序尾段的记录按"互不共享顶点"分层（同层可并行，层间按序），逐位一致。
整体 A/B 测不出提升（8 线程 0.93–0.99，4 线程 1.01–1.04，1 线程 1.03）。用 `bench_phase` 在
emir16M 最大分量（832 万节点，尾段 82 万条记录，占 13.8%）上：

| 尾段 前向 / 回代 | 1 线程 | 2 线程 | 4 线程 | 8 线程 |
|---|---|---|---|---|
| main（串行） | 7.0 / 7.1 ms | 7.9 / 7.4 | 8.8 / 8.6 | 9.6 / 10.1 |
| 层调度 | 9.7 / 9.6 ms | 7.3 / 6.9 | 6.4 / 5.8 | 5.3 / 5.2 |

| 全部回放 前向 / 回代 | 1 线程 | 4 线程 | 8 线程 |
|---|---|---|---|
| main | 36.8 / 40.5 ms | 23.2 / 20.7 | 30.9 / 34.2 |
| 层调度 | 47.7 / 44.3 ms | 21.7 / 22.1 | 19.9 / 17.8 |

结论：

1. 层调度本身有效：单个网 8 线程时尾段 9.6 → 5.3 ms，回放约 65 → 38 ms。
2. 按层重排破坏了记录的访存局部性：单线程尾段慢约 40%（7.0 → 9.7 ms），4 线程以上才赚回。
3. 整体求解中两个网并发、各 4 线程，带宽已饱和，收益被抵消，所以整体 A/B 无提升。
4. 可改进：同一层内的记录可以任意排序（互不冲突），按顶点号排序有望找回局部性；服务器上的
   多线程收益需在服务器上验证。

顺带发现：小分量（只有几个块）时，块回放的 `schedule(dynamic,4)` 会把这几个块分给同一个线程
（`grid:200`：5 个块，1 和 8 线程都约 0.6 ms）；16M 的分量有 118–127 个块，不受影响。

热/冷网格（main，前向+回代合计带宽）：

| 用例 | 回放 1 → 8 线程 | 核心 1 → 8 线程 |
|---|---|---|
| `grid:200`（热，L 10 MB） | 14.0 → 15.5 GB/s（只有 5 个块，见上） | 12.4 → 22.3 GB/s |
| `grid:700`（冷，L 146 MB） | 10.5 → 18.0 GB/s | 10.1 → 15.8 GB/s |
| emir16M 最大分量（L 1061 MB） | 6.0 → 7.1 GB/s（4 线程 10.6） | 9.0 → 14.9 GB/s |

环境：i7-1260P 笔记本，WSL2，12 GB；main ef55d72，METIS（order 6），MKL sequential。

## 后续（同日）

**层内按顶点号排序**（`perf/tail-levels`，环境变量实验）：emir16M 最大分量单线程尾段仍为 9.9 / 9.3 ms
（串行 6.3 / 6.6 ms），没有找回局部性——分层后一条记录的邻居分散在后续各层，层内顺序改变不了；
该分支继续不合入。

**块回放改为 `schedule(dynamic,1)`**（已合入）：块之间互不共享顶点，调度方式不影响结果。全部回放
前向+回代：

| 网格（块数） | main 4 / 8 线程 | dynamic,1 4 / 8 线程 |
|---|---|---|
| `grid:200`（5） | 1.33 / 1.24 ms | 0.39 / 0.66 ms |
| `grid:300`（10） | 1.70 / 2.60 ms | 1.32 / 1.16 ms |
| `grid:450`（22） | 4.43 / 4.99 ms | 3.93 / 4.13 ms |
| `grid:700`（53） | 11.2 / 12.4 ms | 10.1 / 11.0 ms |

单线程不变。16M 整体 A/B（每网 120 多个块）：0.99–1.02（噪声内），解逐位相同；`make test`（OpenMP 与串行）通过。

## 核心阶段基准 `bench_core`：超节点合并参数

`test/bench_core.c`（`make bench_core METIS=1`）跳过分量、低度消元和 METIS 排序（占分解时间大头）：

1. `./bench_core dump.bin 6 前缀`：分解一次，经测试钩子 `vsdlss_m3_core_hook`（正常使用为 NULL）把每个分量
   排好序的核心矩阵写成 `前缀.<分量>.core`（PG_DUMP 格式）；16M 的核心文件 150–230 MB。
2. `./bench_core 文件.core "配置1;配置2;..." "1 4 8" 31`：每个配置（若干 `NAME=value` 环境变量，`-` 为默认）
   各做一次超节点分析和数值分解，然后**在同一进程内交替**计时核心求解，给出成对中位数比值，并报告与配置 1 的解差。

emir16M 较大的网（核心 235 万），`VSDLSS_SN_RELAX`（列数门槛 n0,n1,n2 / 零比例门槛 z1,z2,z3）：

| 配置 | L 存储 | 补零 | 超节点 | 1 线程 | 4 线程 | 8 线程 |
|---|---|---|---|---|---|---|
| 默认 4,16,48 / 0.8,0.1,0.05 | 1061 MB | 11.2% | 63.1 万 | 1 | 1 | 1 |
| 严格 0（不合并） | 943 MB | 0% | 149.7 万 | 1.000 | 1.135 | 1.036 |
| 轻度 2,8,32 / 0.5,0.05,0.02 | 1004 MB | 6.1% | 70.4 万 | 0.937 | 0.966 | 0.997 |
| 重度 8,32,64 / 0.8,0.2,0.1 | 1178 MB | 20.0% | 59.5 万 | 1.079 | 1.171 | 1.133 |

整体求解同进程 A/B（`ab_dl` 新增 `ENV_A`/`ENV_B`，在两次分解前分别设置环境变量），轻度对默认：emir16M
0.968 / 0.968 / 0.974（8/4/1 线程），pgb_16M 0.774（噪声大）/ 0.962 / 0.955；严格对默认 1.000–1.111（更慢）。
解与默认不逐位相同（分解运算顺序变了），后向误差同量级（3.5e-17 → 3.9e-17，8.1e-17 → 8.3e-17），
与默认解的相对差 1–3e-13。

结论：轻度合并使求解快约 3–4%（L 少 5–6%，超节点多 11%），严格不合并因超节点翻倍反而更慢，重度更慢。
默认值未改（改动需放宽"与 main 逐位一致"的要求）；需要时可设 `VSDLSS_SN_RELAX=2,8,32,0.5,0.05,0.02`。
