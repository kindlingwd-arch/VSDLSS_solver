# 求解阶段的重叠与流水线：实验记录（2026-10-17）

讨论的问题：M3 求解阶段除稠密内核之外（收集、低度消元前代回放、core 三角求解、回代回放、写回），能不能让各段交叠执行，打破段与段之间的全局等待。

结论：

- 在一个连通网内部，前代和回代不可能交叠。可以交叠的只有两处：前代回放和 core 前代之间，core 回代和回代回放之间（数据流流水线）。
- 静态模型在 6100 万结点线上用例上估计，两侧都做流水线每网可省约 11 ms（约 10%）。
- 做了回代侧原型（`VSDLSS_PIPE_BWD=1`，默认关闭，结果逐位相同）。服务器实测每网只省约 2 ms（core + 回代回放 48 → 46 ms），不到模型估计的一半，折算到整次求解约 1%。
- 原型保留为默认关闭的开关；前代侧暂不做。
- 用接口响应 H 把局部回放和 core 解耦的方案，因为要多做两遍稀疏乘，是负收益，不做。

## 1. 求解流程与依赖

每个连通分量（VDD、GND 两个网各一个，两个网并发求解）：

1. 收集（两遍分桶置换）；
2. 低度消元前代回放：块并行段，然后是尾部（窗口调度，线上用例只有一个窗口，块 = 尾部的连通块）；
3. core 超节点三角求解：前代从叶子到根，回代从根到叶子；子树并行，树顶按顺序或按分支（BLAS 构建默认按分支）；
4. 回代回放：先尾部，后块并行段；
5. 写回。

**一个连通网内，前代和回代的交叠严格为零。** core 的消去树只有一个根：根的前代要等所有前代回放把更新送到；根的回代是所有回代的起点。所以任何一个回代任务都依赖全部前代任务。能交叠的只有：

- 前代侧：某个 core 子树收齐所有尾部块对它的更新后，就可以开始前代，不必等全部回放结束；
- 回代侧：某个尾部块读到的 core 结点都已在 core 回代中算完后，就可以开始回代回放，不必等 core 全部结束；
- 两个网之间（本来就并发）、相邻时间步之间。

## 2. 线程扫描（服务器，双路 AMD EPYC 7H12，PACKED=0）

两网并发，每格取较慢的那个网，单位 ms：

| 总线程 | 收集 | 前代回放 | core | 回代回放 | 写回 | 单次求解中位数 |
|---|---|---|---|---|---|---|
| 2 | 396 | 357 | 105 | 337 | 270 | 1458 |
| 4 | 214 | 197 | 66 | 164 | 140 | 782 |
| 8 | 119 | 95 | 32 | 82 | 75 | 402 |
| 16 | 61 | 65 | 23 | 49 | 42 | 241 |
| 32 | 34 | 40 | 28 | 32 | 28 | 165 |

32 线程这一行取自 10-15 的运行，当时机器负载较高。

- 除 core 外，各阶段从 16 到 32 线程仍有 1.5–1.8 倍加速。
- core 在每网 8 线程以上不再变快：每网 8 线程 23 ms，每网 16 线程 28 ms。
- 所以每网 16 线程时，core 期间约有一半线程是闲的，这是流水线可以利用的空间，上限约每网 11.5 ms。

## 3. 用接口响应解耦：不做

思路：把消去结点写成 `x_I = z − H·x_core`，局部回放就不必等 core。

测量工具：`test/bench_overlap.c`、`tools/overlap_test.sh`。

- H 很稀疏：每个消去结点只依赖不超过 4 个 core 结点，平均 2.95 个；Hᵀ 每列平均 40 个非零。
- 但要多做两遍稀疏乘（`Hᵀb` 和 `z − H·x_core`），每遍都要把整个网扫一遍，代价和一遍回放差不多。
- 4 核机器（1190 万结点的网）实测，比现在的流程慢 66%。
- 按服务器每网 16 线程估算：能省约 11.5 ms，但要多付约 26 ms，净慢约 14 ms。
- 核再多也一样：能省的部分有上限 t_core，多付的部分始终和一遍回放差不多。

## 4. 流水线的静态分析

工具：

- `test/export_pipeline.c`：按线上方式分解一次，导出 core 超节点树（父结点、存储量）和每个回放单元（块并行段、尾部连通块）的记录数及它连到的 core 超节点；
- `tools/pipeline_analysis.py`：纯 Python，读导出文件，计算就绪曲线，并用列表调度模拟“段间全局等待”和“按依赖就绪执行”两种做法；
- `tools/pipeline_test.sh`：一键运行。

模型假设：每个工作单元按单线程算，回放随线程数线性加速，core 最多同时用 8 个线程，不模拟内存带宽和 NUMA。

6100 万结点线上用例（每网 16 线程，时间按实测换算）：

| | VDD 网（3300 万结点） | GND 网（2809 万结点） |
|---|---|---|
| core | 73 万结点，23 万个超节点 | 68 万结点，21 万个超节点 |
| 回放单元 | 504 个块并行段 + 6209 个尾部连通块 | 429 + 5648 |
| 前代回放完成 25/50/75/90% 时，可开始的 core 前代工作 | 14.8 / 36.8 / 64.4 / 86.4% | 13.9 / 33.7 / 64.6 / 82.1% |
| core 回代完成 25/50/75/90% 时，可开始的回代回放工作 | 3.6 / 22.9 / 47.8 / 67.4% | 1.4 / 28.7 / 52.3 / 62.5% |

| 做法（每网，ms） | VDD 网 | GND 网 |
|---|---|---|
| 现在（段间全局等待） | 109.8 | 109.5 |
| 只做前代侧 | 104.9（−4.9） | 104.5（−5.1） |
| 只做回代侧 | 104.3（−5.5） | 104.6（−4.9） |
| 两侧都做 | 98.7（−11.1） | 98.5（−11.1） |

对比：2288 万结点合成网格以块并行段为主（尾部约 10%），core 要到回放几乎结束才就绪，两侧都做每网只省 3.3 ms。线上用例尾部占 99.6%，6000 多个连通块各自只连到 core 的局部区域，所以就绪得早得多。

## 5. 回代侧原型

开关：`VSDLSS_PIPE_BWD=1`（默认关闭；测试中用 `vsdlss_m3_pipe_bwd` 设置）。

适用条件：尾部是窗口调度且只有一个窗口、core 已按求解顺序重编号成连续、在内存中求解。不满足时走原路径。

实现：

- `vsdlss_sn_solve_inplace_hooked`：core 回代每完成一个超节点就调用一次钩子。按顺序树顶、按分支树顶、子树并行区、串行路径都有。算术和 `vsdlss_sn_solve_inplace` 完全相同。
- `vsdlss_reduce_core_bwd_pipelined`（`src/vsdlss_reduction.c`）：
  - 每个尾部块记录它读到的 core 超节点个数。超节点到块的 CSR 在第一次使用时构建，缓存在 reduction 里。
  - 钩子把对应块的计数减一；减到零时，如果正处在 core 求解的并行区里，就作为 OpenMP 任务执行这个块的回代回放，否则先放进待办列表，下一个并行区开始时再提交。
  - core 求解返回后，补做剩下的块；然后由 `vsdlss_reduce_backward_blocks_inplace` 做块并行段。
- 每条记录读到的值和原路径相同，所以解逐位相同。

测试：

- `test_m3` 的 `test_pipe_bwd`：1/2/4 线程，树顶按顺序和按分支，`solve` 和 `solve_many`，开关前后逐位比对（每种设置求解两次，第二次用缓存的结构）。
- `make test` 全部通过；OPENMP=0 构建和 ASan/UBSan 下的 `test_m3` 通过。
- 2288 万结点合成数据（4 核，ordering 5）：开关前后解的 hash 相同；时间差在噪声内。

服务器 A/B 工具：

- `examples/transient_driver.cpp`：`X_HASH=1` 时，每步输出解的 FNV 哈希。
- `tools/pipe_bwd_test.sh <源码目录> [线程] [步数] [轮数]`：
  - 自动编译 transient_driver：METIS，并自动查找 MKL（`MKLROOT`、`ldconfig`、oneAPI/conda 常见位置）；也可以用 `BUILD` 指定；没有 BLAS 时打印警告。
  - 默认 `OMP_PROC_BIND=spread OMP_PLACES=cores`。不绑核时，双路机器上同一设置两次运行能差 50% 以上。
  - 计时（开关交替多轮，不开 trace）、逐位比对（hash）、分阶段 trace 中位数。

服务器实测（6100 万结点，32 线程，MKL，绑核；每网，trace 中位数，ms）：

| 阶段 | 关 | 开 |
|---|---|---|
| core | 20 | — |
| 回代回放（尾部约 26 + 块约 2） | 28 | — |
| core + 尾部回代 | — | 44 |
| 回代回放（块） | — | 2 |
| **合计** | **48** | **46（−2，−4%）** |

- 所有运行解的 hash 相同；2 个网 × 4 次求解都走了流水线。
- 其他阶段开关前后不变（前代回放 37/36，写回 31/31）。
- 两网并发，整次求解约省 2 ms，约 1%，小于运行之间的波动。
- 之前一次没有 MKL、没有绑核的运行：core + 回代 104 → 90 ms。core 慢、闲置线程多时，重叠得更多。

**为什么只有模型的一半不到：** 44 ≈ 20 + 24，尾部回代基本在 core 结束后才做。可能的原因有两个，这次的数据还区分不开：

1. 依赖来得晚：回代从根往叶子走，尾部块依赖的多是靠近叶子的超节点，要到 core 回代快结束才完成（模型：core 结束时约 63–67% 的块就绪）；
2. 带宽：core 回代本身已用掉约 95% 的读带宽，尾部任务提前开始也只是和 core 抢带宽。模型没有考虑这一点。

## 6. 结论与后续

- 回代侧流水线保留为默认关闭的开关，不再继续投入。
- 前代侧（模型 −5 ms/网）实测大概率同样只剩一半左右，而实现更复杂（要按 core 子树重排尾部块，还要把延后的 core 累加按原消元顺序拆到各子树），暂不做。
- 如果以后要继续：先在 trace 里输出“core 结束时尾部已完成的比例”，判断是依赖还是带宽限制。只有依赖限制时，调整 core 回代的分支优先级才有意义。
- 收益更大的方向仍是：调用方按内部顺序组装右端项和读取解，省掉收集和写回；以及跨时间步合并回放（第 k 步回代和第 k+1 步前代按块连着做）。
