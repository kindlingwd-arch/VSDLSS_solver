# 求解阶段调优实验：带宽、负载均衡与分阶段线程数（2026-10-20 至 10-22）

线上 6100 万结点双网 EMIR 用例，服务器双路 AMD EPYC 7H12（2 × 64 核，每 4 核一个 CCX、共享 16 MiB L3，每颗 CPU 8 个内存通道），MKL 单线程，生产 NUMA 设置（`VSDLSS_INTERLEAVE=1 VSDLSS_NUMA_PLACE=1`）。

## 0. 结论

| 改动 | 结果 | 状态 |
|---|---|---|
| 尾部连通块从大到小调度（`VSDLSS_TAIL_LPT`） | 尾部回放利用率 83–87% → 94–98%（16 线程）；每步 −3.1%（32 线程）/ −8.3%（64 线程）；逐位不变 | **默认开启** |
| 收集和写回单独线程数（`VSDLSS_PERM_THREADS`） | 32 线程 + 收集写回 64 线程：收集 31 → 19 ms，写回 27 → 22 ms；与上一项合计每步 **138.0 → 121.0 ms（−12.3%）**；逐位不变 | 开关，生产推荐 `VSDLSS_PERM_THREADS=64` |
| core 单独线程上限（`VSDLSS_CORE_THREADS`） | 用于 64 线程运行时把 core 限在 8–16 线程；逐位不变 | 开关，服务器未测 |
| 两个连通块交错执行（`VSDLSS_TAIL_ILP=2`） | 本地合成网格 4 线程快约 30%，服务器上回代慢 6–19% | 无效，默认关闭 |
| 64 线程 | 只有收集、写回变快；回放和 core 变慢（每个 CCX 两个线程、共用 L3） | 生产保持 32 线程 |
| core 主干并行化、合并每条记录的访存流 | 上限各约 3 ms，不确定 | 未做 |

生产推荐设置（32 线程）：

```bash
OMP_PROC_BIND=spread OMP_PLACES=cores VSDLSS_INTERLEAVE=1 VSDLSS_NUMA_PLACE=1 VSDLSS_PERM_THREADS=64
```

（`VSDLSS_TAIL_LPT` 已默认开启。）

**判断：** 在"每步在 CPU 上做一次直接法求解"的框架里，剩下的每一项都是个位数毫秒。回放受访存延迟随并发增加而变长的限制，core 受关键路径和调度开销限制，都不是程序结构上的浪费。更大的空间在求解器之外：仿真器每步的完整时间（组装 b、输出电压）、按打包顺序读写省掉收集写回、减少时间步数。

## 1. 机器带宽上限（`tools/perf_profile.sh`，perf_profile_1021_0955，负载约 3.3）

`bench_stream`，每个数组 1 GiB：

| 线程 | copy | triad |
|---|---|---|
| 16 | 186.7 GB/s | 209.5 GB/s |
| 32 | 202.1 | 202.2 |
| 64 | 203.6 | 201.1 |
| 128 | 202.3 | 202.4 |

**上限约 200 GB/s，16 线程就已达到。** 早先版本的 read 一栏只用一个累加器，测到的是加法依赖链（16 线程 75 GB/s、64 线程 225 GB/s），不是带宽；之后改成 8 个独立累加器。

同一次运行的 `bench_phase`（最大的网，3214 万条尾部记录，L 208 MB）：

| 线程 | 回放前代 / 回代 | 记录带宽 | core |
|---|---|---|---|
| 16 | 30.0 / 25.8 ms | 45 GB/s | 18.1 ms（23 GB/s） |
| 32 | 19.6 / 18.2 | 67 GB/s | 17.4 |
| 64 | 15.9 / 19.5 | 71 GB/s | 19.6 |

回放只用到上限的约三分之一，core 只用到约八分之一：**都不受带宽限制。**

`perf`（服务器 perf 3.10，`perf_event_paranoid = 2`；`perf stat` 自动退回用户态计数，`perf record` 要显式用 `-e cycles:u`，且附加到进程（`-p`）会为每个线程 × 每个 CPU 开一个事件、超出文件描述符上限，改为让 `perf record` 直接启动程序）：

| 函数 | 周期占比 |
|---|---|
| `gomp_barrier_wait_end`（并行区之间空等，主要是 `bench_phase` 单线程 `memcpy` 重置向量和分解的串行部分） | 29.0% |
| `forward_tail` | 25.4% |
| `gomp_team_barrier_wait_end`（并行区内屏障等待） | 16.8% |
| `backward_tail` | 10.4% |

IPC 0.99。整体占比不能换算成某一阶段的利用率（还混有分解和基准本身的开销，线程睡眠时也不计周期），据此推出的"回代利用率 ≤ 44%"被第 2 节的直接测量否定。

## 2. 尾部回放的负载均衡（`tools/tail_balance_test.sh`）

新增 `VSDLSS_TAIL_STATS=1`：每次尾部前代、回代打印墙钟时间、各线程在连通块里的时间之和、利用率（和 ÷（线程数 × 墙钟））、最忙线程和最长连通块。

tail_balance_1021_1616（负载约 3.1–3.5），单个网：

| 模式 | 线程 | 前代墙钟 / 利用率 | 回代墙钟 / 利用率 | 最长连通块（前 / 回） |
|---|---|---|---|---|
| 按编号顺序 | 16 | 27.73 ms / 83.4% | 25.12 ms / 87.4% | 7.41 / 6.18 ms |
| 按编号顺序 | 32 | 18.02 / 73.5% | 17.54 / 79.0% | 8.24 / 8.44 |
| **从大到小** | 16 | **24.19 / 93.5%** | **22.68 / 97.5%** | 7.70 / 6.15 |
| **从大到小** | 32 | **14.88 / 89.9%** | **14.66 / 94.3%** | 8.48 / 8.14 |
| 从大到小 + 两块交错 | 16 | 25.59 / 95.5% | 26.65 / 97.2% | 14.97 / 15.37 |
| 从大到小 + 两块交错 | 32 | 17.92 / 84.2% | 20.84 / 83.2% | 17.32 / 20.80 |

三种模式结果逐位相同。

- **从大到小调度**：原来连通块按编号动态分发，约 88% 的记录集中在少数大连通块里（最大约 37 MiB），大块排在后面时其他线程空等。改为按记录数从大到小分发后，最忙线程的时间基本等于墙钟，最长连通块小于墙钟，不再有拖尾。同一窗口内的连通块互不依赖、对 core 的延后更新写在固定槽位，所以顺序不影响结果。
- **两块交错执行**（一个线程每次取两个连通块，记录交替执行）：线程干活的总时间增加 8%（前代）和 17%（回代）。两个连通块一起争用 L2、L3，未命中增多，超过了两条依赖链重叠的好处；而且按大小顺序两两配对，最大的两块落在同一线程，最长任务翻倍。本地 `bench_tail`（400 万结点合成网格，4 核）上 4 线程快约 30%，只说明合成网格的连通块小、缓存压力小。结论：在服务器上无效。

## 3. 回放的线程扩展：每条记录的时间

tail_balance_1021_1206 的 `bench_phase`（按编号顺序），尾部 3214 万条记录：

| 线程 | 前代 / 回代 | 每线程每条记录（前代） |
|---|---|---|
| 1 | 261.2 / 259.6 ms | 8.1 ns（约 21 个周期） |
| 2 | 147.1 / 110.5 | 9.2 |
| 4 | 91.4 / 58.8 | 11.4 |
| 8 | 50.8 / 45.4 | 12.6 |
| 16 | 29.4 / 26.6 | 14.6 |
| 32 | 19.6 / 20.2 | 19.5 |
| 64（perf_profile_1021_0955） | 15.9 / 19.5 | 31.7 |

- 单线程每条记录约 8 ns，记录读取只有约 4.8 GB/s（单核顺序读约 20 GB/s）：单线程受依赖链和访存延迟限制。
- 线程增多时，每个线程处理一条记录的时间持续变长，而总带宽远低于上限：**同时访存的线程越多，每次访问的延迟越长**（内存控制器、插槽互联的排队）。
- 超过每个 CCX 一个线程（64 线程）后，两个线程共用 16 MiB L3，每条记录的时间再跳到约 32 ns，线程翻倍几乎全被抵消。

**为什么生产时一个网的回放（约 29 ms）比 `bench_phase` 的 T=32（约 19 ms）慢约 10 ms：** 生产 32 线程分给两个网，每个网 16 线程，对应 T=16（28.8 / 26.2 ms），和生产一致；两个网同时跑本身几乎没有额外代价。`bench_phase` 的 T=32 是一个网独占两颗 CPU 的 32 个 CCX 和 16 个内存通道；生产给每个网 32 线程（共 64 线程）时，每个网只有一颗 CPU，必然每个 CCX 两个线程，状况接近 T=64。两个网先后求解、各用满整台机器：前代约 18.8 + 16 ≈ 35 ms，比同时求解的约 29 ms 还慢。

## 4. core 求解

### 4.1 线程扩展（tail_balance_1021_1616 第 3 步）

| 线程 | 1 | 2 | 4 | 8 | 16 | 32 |
|---|---|---|---|---|---|---|
| core 前代 + 回代 | 108.3 ms | 47.8 | 26.1 | 19.4 | 18.4 | 17.6 |

1 → 8 线程快 5.6 倍，之后基本不变：core 大部分可以并行，但 8 线程以上不再变快。

### 4.2 关键路径（`tools/core_path_test.sh`，core_path_1021_1632）

`bench_phase` 新增 core 关键路径统计：超节点树里从根到叶最重的那条链，不管多少线程，单方向求解都要逐个读完。

| 项目 | 数值 |
|---|---|
| L | 208 MB（三角块 42 MB） |
| 最重的链 | 12.8 MB（6.2%），18 个面板；三角块 5.9 MB，外部块 6.9 MB |
| 链上最大的面板（宽度 w、外部行 e、大小） | w 791 e 0 2.51 MB（根，纯三角）；w 680 e 415 4.11 MB；w 523 e 381 2.69 MB；w 176–179 e 624–639 各 1.02 MB；其余 13 个合计约 1.5 MB |

单线程读取速度约 3.85 GB/s（1 线程 108 ms 读 416 MB），链的串行时间约 12.8 MB × 2 ÷ 3.85 GB/s ≈ **6.6 ms**，与按 1、8 线程反推的串行比例（约 6%，约 7 ms）一致。

16 线程时 core 约 18.8 ms ≈ 关键路径 6.6 ms + 可并行部分理想地平分（约 102 ÷ 16 ≈ 6.4 ms）+ **调度和同步开销约 6 ms**。理论下限约 13 ms，每步最多省约 6 ms。

### 4.3 分阶段（`tools/core_profile_test.sh`，core_profile_1021_1838）

求解器原有的 `VSDLSS_SOLVE_PROFILE=1` 增加了最大子树统计：树顶按分支并行，树顶占 L 的 19.3%；最大的子树只占 L 的 3.3%，而每个线程理想分到的子树量约 10.1%，**子树阶段是均衡的**，多出的开销不在这里。四段的时间因汇总脚本解析错误（同一行里 "top by branches: fwd bwd" 又出现了 fwd、bwd）没有取到，脚本已修正，可以用 `tools/core_profile_summary.sh <profile.log>` 从原始日志重新汇总。

### 4.4 树顶用内置内核并行（ab_test_1021_1034，无 NUMA 设置，20 步，只看了第 1 轮）

| 组 | 设置 | 第 1 轮中位数 |
|---|---|---|
| c1 | 默认：MKL，树顶按分支并行 | 232.8 ms |
| c2 | `VSDLSS_TOP_BRANCHES=0`：树顶按顺序 | 266.9 ms（+15%） |
| c3 | `VSDLSS_BLAS_SOLVE_MIN=0`：内置内核，大面板分给一组线程 | 389.3 ms（+67%） |
| c4 | 内置内核 + 按分支 | 437.8 ms（+88%） |

内置内核在宽面板上远不如 MKL，用它换取树顶并行是负优化；按分支并行（c1）是对的。这也说明 core 树顶若要并行化，只能保留单线程 MKL、把一次调用按固定的行块（前代 `dgemv`）或列块（回代转置 `dgemv`）拆给空闲线程；它只能覆盖关键路径上的外部块（6.9 MB，约 3 ms）。根面板没有外部行，只有三角求解，MKL 的单次 `dtpsv` 无法拆分。

MKL 保持单线程（`MKL_THREADING_LAYER=SEQUENTIAL`）的原因：求解器已有两层 OpenMP 并行，多线程 MKL 会嵌套超订；单线程调用顺序固定，保证任意线程数结果逐位一致；绝大多数 BLAS 调用很小；GCC 的 libgomp 与 MKL 默认的 libiomp5 两套运行库冲突。

## 5. 分阶段线程数

64 线程（每个网 32 线程）时，只有收集和写回变快，回放和 core 变慢（ab_test_1020_2022，见 [solve-strategy-catalog](solve-strategy-catalog-20261019.md)）。所以按阶段给线程：

- `VSDLSS_PERM_THREADS=n`：两遍法收集和写回用 n 个线程（最多 64）。只搬数据，逐位不变（`test_parallel`）。
- `VSDLSS_CORE_THREADS=n`：每个网的 core 求解最多 n 个线程。树并行求解在任何线程数下逐位相同（`test_m3`）。

### 5.1 32 线程（ab_test_1022_1343）

| 组 | 设置 | 各轮中位数 | 中位数的中位数 | 最快 |
|---|---|---|---|---|
| c1 | 生产设置（交错 + 按使用者放置），按编号顺序 | 143.9 / 137.1 / 138.0 ms | 138.0 ms | 134.9 |
| c2 | + 从大到小 | 139.3 / 133.8 / 132.3 | 133.8（−3.1%） | 127.4 |
| **c3** | **+ `VSDLSS_PERM_THREADS=64`** | **123.1 / 121.0 / 119.6** | **121.0（−12.3%）** | **112.9** |

| 阶段（trace，ms） | c1 | c2 | c3 |
|---|---|---|---|
| 收集 | 31 | 31 | 19 |
| 前代回放 | 33 | 30 | 30 |
| core | 21 | 19 | 21 |
| 回代回放 | 29 | 26 | 26 |
| 写回 | 27 | 27 | 22 |

三组 hash 都是 `3b2d5f296982a0ae`。

### 5.2 64 线程（ab_test_1022_0922）

| 组 | 设置 | 中位数 | 最快 |
|---|---|---|---|
| c1 | 生产设置，按编号顺序 | 154.1 ms | 133.5 |
| c2 | + 从大到小 | 141.3 ms（−8.3%） | 128.5 |

| 阶段（trace，ms） | c1 | c2 |
|---|---|---|
| 收集 | 19 | 19 |
| 前代回放 | 34 | 32 |
| core | 39 | 31 |
| 回代回放 | 31 | 23 |
| 写回 | 22 | 22 |

64 线程加从大到小调度后，除 core 外各阶段都不慢于 32 线程。若把 core 限在每网 8–16 线程（`VSDLSS_CORE_THREADS`，回到约 18 ms），按上表估算每步约 114 ms。这组没有在服务器上测；64 线程要占一半物理核，机器不独占时波动更大。

## 6. 讨论过、没有做的

| 思路 | 判断 |
|---|---|
| 合并每条记录的访存流（下标与乘子交错存放、延后标记并入下标高位） | 字节数不变，只减少数据流和指令；回放不受带宽限制、顺序流由硬件预取处理，估计 0–10%，而打包格式在很多地方用到，改动大 |
| core 主干按行块 / 列块拆分 MKL 调用 | 上限约 3 ms；结果与现在差一个舍入（块大小固定，任意线程数之间仍逐位一致） |
| core 调度开销（约 6 ms） | 原因未定位；收回一半约 2–3 ms |
