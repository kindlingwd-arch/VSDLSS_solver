# 2026-10-13 性能历史：从第一个完整版本到现在

## 结论

| 对比 | 求解 | 分解 | 峰值内存 |
|---|---|---|---|
| 400 万结点 EMIR，第一个完整版本（09-10）→ 现在 | 712 → 约 74 ms，**约 9.6 倍** | 2229 → 约 5.5 s，**约 400 倍** | 6.83 → 1.04 GB，约 1/6.5 |
| 1600 万结点 EMIR，09-22 → 现在 | 1324 → 约 300 ms，**约 4.4 倍** | 80 → 约 30 s，约 2.7 倍 | 8.66 → 4.3 GB，约一半 |
| 6100 万结点双网 EMIR（服务器 32 线程），10-10 → 现在 | 约 2.1 s → 0.17 s，**约 12 倍** | 基本不变（约 35 s） | 求解时常驻内存少 2.5 GB |
| 同一用例，对比用户原有的求解器 | 1.4 s → 0.17 s，约 8 倍 | — | — |

- 第一个完整版本在 400 万结点用例上分解就要 37 分钟，1600 万和 6100 万结点用例在它上面无法在合理时间内完成，所以没有直接对比。
- 各版本的 backward error 都在 1e-17 至 7e-17 之间。

**时间线**：

- 2026-09-08 建库，到 10-11，约 5 周。
- 105 个提交、40 多个 PR。
- 过程记录在本目录 40 多篇文档里。
- 第一个完整版本保留为分支 `release/v1.0`（c313d8a）。

## 方法

### 版本

从 main 的历史里选出 6 个关键点：

| 阶段 | 提交 | 日期 | 内容 |
|---|---|---|---|
| 0 | c313d8a | 09-10 | 第一个完整的 M3 求解器（`release/v1.0`） |
| 1 | 8e90ef6 | 09-22 | 排序（修复最小度 O(n³) 选择、AMD）与超节点内核优化 |
| 2 | 0db32ea | 09-22 | 电源网格预处理：BFS 重编号、分块并行低度消元、并行求解、默认 AMD |
| 3 | 590190b | 09-25 | 双网并行、打包回放、METIS、AVX2、两遍置换 |
| 4 | 6f8eafe | 10-10 | relabel、内存压缩、前代改进、BLAS 树求解、连通分量加速 |
| 5 | 711ed08 | 10-11 | 尾部按层并行、窗口调度 + core 累加延后 |

### 测试程序

`test/bench_history.c`（`make bench_history`）对所有版本使用同一份代码：

1. 用 `dlopen` 加载某个版本编译出的共享库。
2. 读入 PG_DUMP 用例，用 `vsdlss_factorize_m3` 分解。
3. 做 1 次冷求解和 7 次热求解（原始编号接口 `vsdlss_m3_solve`），热求解取中位数。
4. 报告 backward error 和峰值 RSS。

公共接口（`vsdlss_spalloc`、`vsdlss_set_num_threads`、`vsdlss_factorize_m3`、`vsdlss_m3_solve`）从第一版起没有变化。

各版本直接从提交编译成共享库：

```bash
git archive <commit> src include | tar -x -C /tmp/v
cd /tmp/v && gcc -O2 -fPIC -shared -Wl,-Bsymbolic -Iinclude -std=c11 -fopenmp \
  -DVSDLSS_BLAS -DVSDLSS_METIS -DVSDLSS_METIS_THREADSAFE -I<metis>/include \
  -o lib.so src/vsdlss*.c <metis>/libmetis.a -lm -L<mkl>/lib -l:libmkl_rt.so.3
```

- 早期版本没有 BLAS 和 METIS 的代码，这些宏对它们不起作用。
- 每次运行单独一个进程。

### 环境

- i7-1260P 笔记本，WSL2，GCC 9.4。
- 8 线程，`OMP_PROC_BIND=close OMP_PLACES=cores MKL_THREADING_LAYER=SEQUENTIAL`。
- 排序：每个版本用当时的最佳配置。阶段 0 只有 MLD；阶段 1、2 用 AMD；阶段 3 起用 METIS。

## 结果

### 400 万结点 EMIR（`emir4000000.bin`）

第一轮之后，阶段 1–5 又交替重跑了两轮；阶段 5 和阶段 4 另做了三轮交替对比。

| 阶段 | 版本 | 排序 | 分解 | 热求解（各轮） | 峰值内存 |
|---|---|---|---|---|---|
| 0 | c313d8a | MLD | **2229 s** | **712 ms** | 6.83 GB |
| 1 | 8e90ef6 | AMD | 10.4–11.2 s | 241 / 259 / 294 ms | 2.00 GB |
| 1 | 8e90ef6 | MLD（默认） | 32.9 s | 286 ms | 2.20 GB |
| 2 | 0db32ea | AMD | 6.6–7.5 s | 233 / 202 / 204 ms | 1.5–1.7 GB |
| 3 | 590190b | METIS | 5.2 s | 172 / 109 / 113 ms | 1.26 GB |
| 3 | 590190b | AMD | 5.3 s | 164 ms | 1.46 GB |
| 4 | 6f8eafe | METIS | 5.4–6.2 s | 69 / 74 / 75 / 92 / 76 / 73 ms | 1.04 GB |
| 5 | 711ed08 | METIS | 5.1–6.8 s | 71 / 81 / 83 / 69 / 79 / 72 ms | 1.04 GB |

这个用例的尾部很小：两个分量的尾部分别只有 49,729 和 76,513 条记录，窗口调度下 1 个窗口，延后的 core 更新只有 2 条。所以阶段 4 和 5 差别在噪声范围内。

交替三轮：

| 配置 | 热求解平均 |
|---|---|
| 窗口调度 | 73 ms |
| 按层并行（`VSDLSS_TAIL_WINDOWS=0`） | 77 ms |

**测量注意**：第一轮里阶段 5 的数据（分解 30.8 s、热求解 315 ms）是编译后第一个进程的冷启动异常，WSL 虚拟机还在扩充内存。它在后续五轮中都没有再出现，所以已经排除。

## 各阶段的贡献

1. **阶段 0 → 1：分解从分钟级降到秒级。**
   - 修复最小度排序的 O(n³) 选择，加入 AMD，去掉串行的符号分析瓶颈，重写并行内核（[13](13-parallel-efficiency.md)、[15](15-ordering-amd.md)、[16](16-main-integration-20260921.md)）。
   - 400 万结点：分解 2229 → 约 10 s（约 200 倍），求解 712 → 约 265 ms。
2. **阶段 1 → 2：针对电源网格的预处理。**
   - BFS 局部性重编号；低度消元按 65536 结点分块并行；求解并行化，并缓存求解工作区（[18](18-powergrid-preprocessing-20260922.md)、[19](19-single-solve-efficiency-20260922.md)）。
   - 1600 万结点：求解 1324 → 954 ms，分解 80 → 55 s。
3. **阶段 2 → 3：求解路径重做。**
   - VDD / GND 两个网同时求解；低度消元记录压缩为打包格式回放；可选 METIS（填充少 20–48%）；AVX2 内核；gather / scatter 改为两遍分桶置换（[20](20-vdd-gnd-components-20260923.md)、[metis](metis-ordering-20260924.md)、[perm2](perm2-wc-nt-20260926.md)）。
   - 1600 万结点：求解 954 → 510 ms，分解 55 → 31 s。
4. **阶段 3 → 4：细节与内存。**
   - 按求解顺序重编号（relabel）；32 位下标与面板压缩（[memory](memory-reduction-20260925.md)）；前代改为推送形式；BLAS 求解保持树并行（[blas-tree](blas-tree-solve-20261010.md)）；连通分量阶段加速（[components](components-phase-20261009.md)）。
   - 1600 万结点：求解 510 → 280 ms，内存 4.9 → 4.2 GB。
5. **阶段 4 → 5：尾部回放。**
   - 按冲突层并行，以及窗口调度 + core 累加延后（[tail](tail-replay-optimization-20261011.md)）。
   - 在 400 万、1600 万这类尾部很小的用例上，变化在噪声范围内。
   - 在尾部占 99.6% 的 6100 万结点用例上，求解约 2.1 s → 0.17 s，是这个用例上贡献最大的一步。

## 要点

- **瓶颈因用例而异。** 尾部小的用例，提速主要来自 9 月的前几个阶段；6100 万结点用例几乎全部时间都在尾部，所以最近的尾部优化最关键。性能结论需要在目标数据上实测。
- **大部分提速是在保持结果逐位相同的前提下取得的。** 阶段之间改变排序（MLD → AMD → METIS）时，结果按设计会变化，精度保持在 1e-17 量级；之后的大部分优化（包括尾部的两轮）都与上一版逐位相同，或者是默认关闭的选项（链连续编号）。
- **还可以做的**（见 [tail-replay-optimization-20261011](tail-replay-optimization-20261011.md) §8）：
  - 调用方直接按内部顺序组装右端项、读取解，省掉 gather / scatter（约 57 ms）；
  - NUMA 本地化（`VSDLSS_TAIL_NUMA=1` 实验版，待服务器实测，未合并）；
  - 改为按图划分分块，以缩短分解时间。
- **试过、收益很小的**：求解各段的数据流流水线。回代侧原型（`VSDLSS_PIPE_BWD=1`，默认关闭）在 6100 万结点用例上每网只省约 2 ms；用接口响应解耦是负收益（[overlap-pipeline](solve-overlap-pipeline-20261017.md)）。
- **下一步的设计**：求解器接管时间步进，加上跨时间步融合，以及 FP32 因子、NUMA 放置等待测方向，见 [transient-stepping-design](transient-stepping-design-20261018.md)。
- **NUMA**：运行时加 `VSDLSS_INTERLEAVE=1`，6100 万结点用例每步 563 → 151 ms（避开内核自动 NUMA 平衡造成的缺页），见 [numa-placement](numa-placement-20261019.md)。
- **讨论过的全部求解加速思路及是否有效**：见 [solve-strategy-catalog](solve-strategy-catalog-20261019.md)。
