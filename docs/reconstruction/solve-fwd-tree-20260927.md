# 多线程求解的前代（tree schedule / forward_pull）（2026-09-27）

多线程求解（`solve_tree`）的前代不走面板 push 形式，而是按目标"拉"更新（`forward_pull`）：子树阶段各线程
处理独立子树，树顶阶段按目标顺序、大目标用线程组。前两轮的前代优化只在串行 push 路径上，这里补上。

## 测量方法

本机只有 1 个 vCPU，无法测真实多线程加速。新增钩子 `vsdlss_solve_tree_nt`：强制按 N 线程的切分运行
树调度；配合 `OMP_THREAD_LIMIT=1` 串行执行，测的是该调度的**总工作量**。bench 中配置位 16 表示走树调度。

8M 上原来的树调度（N=8）串行执行比串行 push 慢：前代每分量约 0.097 s（子树 0.075–0.080 + 树顶 0.044），
串行 push 前代约 0.077 s。子树覆盖约 78% 的 L，树顶约 22%。

## 改动（`VSDLSS_SOLVE_V2` 位 8，默认开；每种设置结果逐位相同）

1. **子树阶段改为 push 形式**（`forward_push_subtree`）。子树在后序中是一段连续下标时（`subtree_contiguous`
   逐个检查；8M 和测试中全部满足，不满足时仍走 pull），按下标升序逐个面板做前代，外部更新只推到行号
   小于子树根末列的那段前缀（即子树内的祖先）；落在树顶的行留给树顶目标照旧去拉。子树内每个元素仍按
   源升序、列升序相减，再做自身三角求解，与串行 push 完全一致；各子树只写自己的列，无数据竞争。
2. **pull 的块更新改用 `vsdlss_simd_ext_update`**（16 行留在寄存器），替代 8 行的 `block_update`；
   `forward_pull` 与 `forward_pull_team` 都换。每个元素仍按列升序相减。

## 8M 结果（N 线程切分、串行执行的总工作量，每次解都与参考逐位核对）

| 配置 | N=8 | N=4 |
|---|---|---|
| 树调度，本轮前（位 1/2/4） | 1.000 | 1.000 |
| 树调度，本轮后（+位 8） | 0.920 | 0.912 |
| 相对最初 main 的树调度（N=8） | 0.895（前两轮只贡献 0.977） | |

分阶段（每分量）：子树前代 0.075–0.080 → 0.051–0.058 s（约 −31%），树顶前代 0.044 → 0.039 s。
串行 push 仍更快（配对比值 0.88 vs 0.93），剩余差距主要是树顶拉取子树行尾的块。

真实多线程下，子树阶段按线程并行，节省的是各线程的工作量；墙钟收益取决于负载均衡和带宽，需在多核机器上测。

make bench_solve_back
