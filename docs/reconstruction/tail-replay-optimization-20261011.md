# 2026-10-10 至 10-11 低度消元尾部回放的优化

## 结论

6100 万结点双网 EMIR 用例（服务器，32 线程）的热求解：

| 阶段 | 热求解 | 结果 |
|---|---|---|
| 优化前（main 6f8eafe） | 约 2.1 s | 基准 |
| 按冲突层并行回放尾部（PR #42） | 约 0.29 s | 与串行逐位相同 |
| 默认 grain 改为 2048（PR #42） | 约 0.285 s | 逐位相同 |
| 窗口调度 + core 累加延后（PR #46，默认） | **169–176 ms** | **逐位相同** |
| 再加 `VSDLSS_CHAIN_ORDER=1`（PR #43，默认关闭） | **151–163 ms** | rel_err 2.74e-12 → 2.95e-12 |

- 合计提速约 12–14 倍。
- 分解时间基本不变（约 35 s）。
- 求解时常驻内存从 8.2 GB 降到 5.6 GB，峰值内存不变（约 14.5 GB）。

## 1. 问题：尾部占 99.6%，回放全部串行

之前的分析（见 [solve-replay-layout-20261009](solve-replay-layout-20261009.md) 和 [phase-bench-20261009](phase-bench-20261009.md)）认为求解时间主要在 core 的超节点求解。
在这个用例上，`bench_phase` 测出的情况完全不同。

**低度消元的结构**

| 项目 | 数值 |
|---|---|
| 两个分量 | 3300 万、2809 万结点 |
| 低度消元的记录 | 97.8% |
| 落在块并行之外顺序尾部的记录 | **99.6%**（3214 万条） |

**每次求解的耗时**

| 阶段 | 耗时 |
|---|---|
| 尾部回放（forward + backward） | 约 1.5 s（单线程，和线程数无关） |
| core 求解 | 约 0.02 s |

**尾部为什么这么大**

- 块并行只消去"所有邻居都在同一个 65536 结点块里"的结点。
- 这个电网的 BFS 波前比块还宽，导线链上相邻结点的 BFS 编号相差一整个波前，几乎所有链都跨块。

**依赖结构**

- 把"共享任何结点"算作冲突时，尾部有 666 层，平均每层 4.8 万条。
- 理想情况下能并行，但原实现是一条记录接一条记录地串行回放。

## 2. 按冲突层并行（PR #42）

### 层的定义

- 一条记录的层号 = 与它共享结点的前序记录的最大层号 + 1。
- 同一层的记录互不共享结点，可以并行。
- 每个结点上的运算顺序不变，所以结果与串行逐位相同。

### 初版

- 每层之间同步一次，层内按 32 条记录一块静态划分。
- 笔记本（i7-1260P，4 大核 + 8 小核）上只快约 1.6 倍。
- 对照实验：纯随机读写 64 MB 向量的最简循环，4 线程也只能快 2.2 倍。说明瓶颈是随机访存，不是代码。

### 关键改进

1. **测试补上 solve-order relabel**：真实求解在分解后会按记录顺序重编号结点，主元读取是顺序的。`bench_tail` 原来没做这一步，测得偏悲观。
2. **层内按"第一个写入者"排序**：
   - 同一层内顺序可以任意调整，结果仍逐位相同。
   - 按"最先更新它的记录的位置"排序后，相邻记录访问相邻结点。
   - 单线程也快了约 1.8 倍。
3. **forward plan**：
   - 每层的更新按目标排序后，把目标、乘子、源复制成连续数组（每次更新 16 字节）。
   - 线程写互不重叠的连续区间，forward 只需顺序读 plan。
4. **构建全部改成线性时间并行算法**：
   - 层内排序：原子取最小确定"第一个写入者"，再按线程计数、求前缀和、分配位置。
   - plan：每层并行做基数排序。
   - 打包时直接按新顺序读取记录，不再原地搬动。
   - 分解额外开销：11 s → 2.3 s → 1.1 s（8M 结点，8 线程）。
5. **grain（每线程每层至少处理的记录数）**：
   - 每层记录太少时开太多线程，会卡在同步上：4M 结点、32 线程跑在 16 个 CPU 上时，backward 从 0.06 s 变成 5 s。
   - 服务器实测（6100 万结点，32 线程，整次求解）：

     | grain | 热求解 |
     |---|---|
     | 4096 | 325 ms |
     | **2048（新默认）** | **285 ms** |
     | 1024 | 286 ms |

服务器结果（32 线程，`bench_phase`，3300 万分量）：

| 方式 | 尾部 fwd / bwd |
|---|---|
| 串行 | 639 / 994 ms |
| 层级调度，grain 2048 | 67 / 80 ms |

### 从 PR #41（另一份层级调度实现）采纳的

- 调度和 plan 的内存分配失败时，退回串行，而不是让分解失败。
- 尾部并行区登记实际线程数（`last_team_size`）。
- trace 列出调度占用的内存。
- 直接测试回放：带 / 不带 `saved`、不带 plan、非有限值检测、分配失败扫描。

PR #41 本身在层内保持消元顺序、没有 plan、串行构建，4 线程 backward 只有 1.89 倍，已关闭。

## 3. 链连续编号（PR #43，默认关闭）

`VSDLSS_CHAIN_ORDER=1`：在 BFS 顺序基础上，把每条度为 2 的链连续编号，让更多链在块内消去。

| 用例 | 尾部占比 | 热求解 |
|---|---|---|
| 合成用例 `far`（4M） | 90.1% → 0.9% | 快 8–10% |
| 6100 万结点用例 | 99.6% → 69.2% | 约 290 → 241 ms |

这个电网的大部分尾部结点不在度为 2 的链上，而是电源轨上接着 via、度为 3 的结点。

消元顺序会改变，结果不再逐位相同（rel_err 2.75e-12 → 2.97e-12），所以默认关闭。

## 4. 试过但没有采纳的

| 尝试 | 结果 |
|---|---|
| 层内按目标排序（plan 之前的版本） | 局部性更差，导线用例慢 3 倍，已回退 |
| 软件预取（`VSDLSS_TAIL_PF`） | 交替对比多轮，笔记本上没有稳定收益：层内排序后局部性已经好，硬件预取足够 |
| 固定度数的 AVX2 backward（PR #44） | 层级调度下 4 线程快 13%、8 线程慢 4%；窗口调度下连通块内记录有依赖，用不上；已关闭 |
| 只在笔记本上评估 | 4 线程以后内存带宽饱和，大小核混合，噪声 30–50%；需要服务器确认的都做成了一键脚本 |

## 5. 窗口调度（PR #46，默认）

### 5.1 思路

- 层级调度每层同步一次，而且同一个线程在相邻两层处理的往往是网络里不相干的位置。
- 窗口调度把连续若干层合成一个窗口，窗口内按连通块（共享结点的记录连在一起）分给线程。每块由一个线程按顺序做完，窗口之间才同步。
- 第一版（`K=256`，"共享任何结点"都算冲突）在服务器上：

  | 项目 | 数值 |
  |---|---|
  | 窗口数 | 352 |
  | 尾部 32 线程 fwd / bwd | 53 / 56 ms |
  | 热求解（与链编号合用） | 188 ms |

  窗口并不少：每个窗口平均只合并约 2 层。

### 5.2 依赖统计：冲突大多是假的

在 `bench_phase` 里加了统计（`BENCH_TAIL_DEPS=1`），在服务器的真实数据上运行：

| 冲突规则 | 依赖深度 | K=64 窗口数 | K=256 窗口数 |
|---|---|---|---|
| 共享任何结点（原规则） | 666 | 193 | 352 |
| forward，core 结点不算 | 340 | **1** | **1** |
| backward，只等要读的值 | 340 | **1** | **1** |

许多尾部记录连向同一批 core 结点（网格主干），所有连通块都经由它们粘成了大块。但这些 core 结点：

- **backward**：只被读取，读和读之间不冲突；
- **forward**：只被累加。累加有顺序要求（浮点结果对顺序敏感），但可以单独处理。

### 5.3 实现

- **连通块不再经由 core 结点相连**。尾部通常只剩 1 个窗口，所以每遍回放只同步一次。
- **forward 的 core 累加分两类**：
  - 更新某个 core 结点的记录都能放进同一个连通块，且块不超过尾部的 1/K：把它们并进同一块，块内本来就按原顺序执行，可以直接累加。
  - 其余被多个块共用的 core 结点：并行阶段把乘积写进缓冲区，尾部做完后按 core 结点分组，**按原消元顺序**依次减去。每个乘积的算法不变，减法次序也不变，结果逐位相同。
- **缓冲区按 core 结点分组排列**：最后一步顺序读取。缓冲区保存在 factor 里，所以每次求解不会重新分配、产生缺页。
- **构建全部并行**：
  - 无锁并查集；
  - 按结点编号并行收集每个 core 结点的更新者，多数结点并行判定；
  - 只有更新者分属多个块的结点，按编号顺序串行判定，结果与线程数无关；
  - 单窗口时不计算层号，连通块内按消元顺序执行；单窗口不成立时，才按层逐个扩展窗口（此时所有 core 结点都延后）。
- **安全**：
  - 只在打包路径（M3 实际使用的路径）上启用。
  - `vsdlss_reduce_rhs` / `recover` 遇到窗口布局时返回 `VSDLSS_ERR_UNSUPPORTED`，避免按错误顺序回放。
  - 分配失败时退回串行回放。
  - 窗口布局在 1 线程和 4 线程下构建，逐字节相同。

### 5.4 中途的问题

| 现象 | 原因 | 修正 |
|---|---|---|
| 服务器上 forward 从 65 ms 变成 136 ms（backward 已降到 43 ms） | 起初所有 core 更新都延后，这个电网里数量很多；最后一步在大缓冲区里随机读 | 能并进单个连通块的 core 结点直接累加；剩余的按结点分组顺序读。延后的只剩 1.9% |
| 每次求解多出 3000–7600 次缺页 | 缓冲区每次求解重新分配 | 分解时分配一次，带占用标志复用 |
| 分解多 6–10 s | 合并和延后数据构建是串行的 | 全部并行化，8M 结点上额外开销 +1.73 s → +0.57 s |
| `bench_phase` 显示 blocks fwd 285 ms、1827 levels | 只含块的视图仍带着窗口标志；层数统计对重排后的顺序没有意义 | 回放前检查尾部记录数与调度一致；窗口模式下改为打印窗口、块和延后数 |
| test_m3 段错误 | 没有被尾部更新的 core 结点，其更新者列表为空，却读了第一个元素 | 用 AddressSanitizer 定位后修复 |

### 5.5 最终结果（服务器，32 线程）

**尾部回放**（`bench_phase`，3300 万分量，fwd / bwd）

| 线程 | 层级调度 | 窗口调度 |
|---|---|---|
| 1 | 497 / 684 ms | 249 / 241 ms |
| 16 | 78 / 103 ms | 32 / 27 ms |
| 32 | 69 / 78 ms | **20.5 / 19.0 ms** |

- 1 个窗口，6209 块（每块约 5000 条记录）。
- 延后更新 150 万 / 8048 万（1.9%），涉及 4 万个 core 结点。

**整次求解**（`transient_driver`，两轮）

| 配置 | 热求解 | 分解 | 求解时常驻内存 | rel_err |
|---|---|---|---|---|
| 层级调度（原默认） | 310 / 363 ms | 35.4 / 38.8 s | 8.2 GB | 2.73793e-12 |
| 窗口调度（新默认） | **176 / 169 ms** | 35.9 / 36.6 s | 5.6 GB | 2.73793e-12（相同） |
| 窗口调度 + 链连续编号 | **163 / 151 ms** | 38.3 / 31.5 s | 5.6 GB | 2.95e-12 |

层级调度第 2 轮的 363 ms 是在负载 26–37 时跑的。

**现在的耗时构成**（窗口 + 链编号，约 160 ms）

| 阶段 | 耗时 |
|---|---|
| gather（原始顺序 → 内部顺序） | 30 ms |
| 尾部 forward | 35 ms |
| core | 31 ms |
| 尾部 backward | 29 ms |
| scatter | 27 ms |

尾部已不再是瓶颈。

## 6. 工具

| 工具 | 用途 |
|---|---|
| `test/bench_tail.c`（`make bench_tail`） | 生成尾部占主导的网络（2% 网格 + 随机编号导线）；走与 M3 相同的打包路径和 relabel；同一进程内比较串行尾部和调度回放，并逐位核对；打印分解各步耗时 |
| `bench_phase` + `BENCH_TAIL_DEPS=1` | 统计尾部在三种冲突规则下的依赖深度和窗口数，需要真实数据时先跑它 |

| `VSDLSS_TRACE=1` | 每个分量输出 `tail ... records, N windows, ... chunks, schedule ... MiB, deferred core updates ...` |
| 服务器一键脚本 | `run_bench_tail.sh`、`tail_test.sh`、`grain_test.sh`、`chain_test.sh`、`deps_test.sh`、`window_test.sh`：编译、交替运行各配置、汇总成 `summary.txt` |

## 7. 开关

| 环境变量 | 默认 | 作用 |
|---|---|---|
| `VSDLSS_TAIL_WINDOWS` | 64 | 窗口内最大连通块不超过 1/K；0 = 按层并行 |
| `VSDLSS_TAIL_GRAIN` | 2048 | 按层并行时每线程每层至少处理的记录数 |
| `VSDLSS_TAIL_MIN` | 4096 | 尾部至少多少条记录才建调度；设成很大的数就关闭 |
| `VSDLSS_TAIL_ORDER` | 1 | 层内按第一个写入者排序 |
| `VSDLSS_TAIL_PLAN` | 1 | 按层并行时的 forward plan |
| `VSDLSS_CHAIN_ORDER` | 0 | 链连续编号（结果不逐位相同） |

## 8. 后续可做

- **省掉 gather/scatter（57 ms）**：调用方用 `vsdlss_m3_export_packed_permutation` 和 `vsdlss_m3_solve_packed_inplace`，直接在内部顺序里组装右端项、读取解，每次求解就不用做这两步。`transient_driver` 的 `PACKED=1` 模式在本地暂存（未合并）。
- **core 求解（31 ms）**：双网同时求解时各用一半线程，可评估按分量分配线程。
- **单窗口不成立的电网**：多窗口时所有 core 结点都延后，可以按窗口做同样的合并。
