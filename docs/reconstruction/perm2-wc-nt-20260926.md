# 收集 / 写回：写合并与非临时存储（2026-09-26）

接 `perm2-only-32m-20260926.md`。目标：原始编号接口的收集 + 写回时延降为原来的一半，结果逐位不变。

## 瓶颈在哪里

`test/bench_perm3.c` 把每一遍单独计时（32M 随机置换，1 线程，大页，8 次中位数，ms）：

| 变体 | 收集 | 其中第 1 遍 | 写回 | 其中第 1 遍 | 合计 |
|---|---:|---:|---:|---:|---:|
| 直接循环 | 253 | – | 192 | – | 445 |
| v0 现行两遍 | 437 | 338 | 456 | 337 | 894 |
| v1 +uint16 桶号 | 439 | 340 | 460 | 341 | 899 |
| v2 +第 1 遍写合并、64 B 非临时写出 | 226 | 110 | 225 | 111 | 451 |
| v3 +第 2 遍暂存块、流式写出 | 200 | 110 | 179 | 111 | **378（0.42×）** |

第 1 遍占两遍时间的约 75%。它同时向 B = 977 个桶（每线程）追加，
977 条写流超过 L1 容量，每次写入都是部分缓存行、先读后写（RFO），
带宽和行填充缓冲都花在这上面。单独把 4 B 的 `g2p` 读换成 2 B 的桶号几乎无效（v1），
说明不是读索引的问题，而是写流。

逐字节估算（每元素）：v0 约 54 B（含两次 RFO），v3 约 36 B，且第 1 遍变成顺序整行写。

## 改动（`src/vsdlss_m3.c`）

1. **第 1 遍软件写合并**：每线程每桶一条 64 B 缓冲行（977 × 64 B ≈ 62 KB，驻留 L1/L2），
   攒满 8 个 double 整行写出；n ≥ `vsdlss_perm2_nt_min`（默认 4M）时用 `_mm_stream_pd`，免 RFO。
   为此每个（线程，桶）段起点对齐到 8 个元素，scratch 长度为 n + 8·T·B（32M、8 线程多 4 MB）。
2. **第 2 遍暂存块**：桶先落到线程私有的 256 KB 暂存块（在 L2 内），再顺序（非临时）写到目标；
   有限值检查移到写出循环。跨分量的块仍走逐元素路径。
3. **预存 uint16 桶号**（`bktG` 按原始编号、`bktW` 按打包编号）：第 1 遍不再解码
   `inv32 + offset[]`，写回也不再读 8 B 的 `component_map`。计划多占 4 B/顶点（32M 约 128 MB），
   `VSDLSS_PERM2_BUCKETS=0` 关闭（回到解码，慢约 20%）。
4. scratch 区改为 64 B 对齐、按计划所需长度缓存（`pbuf_len`），末尾放暂存块和写合并行。

开关：`VSDLSS_PERM2_NT=0/1` 强制普通 / 非临时存储；非 x86 或无 SSE2 时自动用普通存储。
小 n（< 4M）默认不用非临时存储：此时向量可留在 LLC，下一阶段更愿意从缓存读到它们。

|---|---:|---:|---:|---:|
| 改前（c3fffd0） | 0.064 / 0.063 s | 0.067 / 0.066 s | 0.131 / 0.129 s | 0.265 / 0.264 s |
| 改后 | 0.035 / 0.034 s | 0.030 / 0.029 s | **0.065 / 0.063 s** | **0.199 / 0.196 s** |
| 改后，`VSDLSS_PERM2_NT=0` | 0.057 s | 0.056 s | 0.113 s | 0.248 s |

## 注意

- 测量机只有 1 个 vCPU、3 GB 内存，且虚拟机报告 260 MB L3：直接循环在这里异常地好
  （单线程下与新两遍相当），8M 时整个向量还在 L3 内。**多线程和真实服务器的数字需要重测**：
  ```sh
  make bench_perm3
  ./bench_perm3 32000000 4 8
  ./bench_perm3 32000000 8 8
  ```
  4/8 线程时带宽成为上限，预期收益来自字节数（约 54 → 36 B/元素）和整行写，可能低于单线程的 2.4×。
- 块大小：服务器 L2 ≥ 1 MB 时可试 `-DSHIFT=16`（512 KB 块）。本机（2 MB L2）v3 再快约 10%，
  但库里的 `PERM_SH` 未改。
- NUMA：scratch 的第 1 遍按线程写入散布在所有桶，多路服务器上首次触摸会交错分布；未测。

## 块大小选择（256 KB / 512 KB）

块大小只影响速度，不影响结果（纯拷贝，逐位相同）。选择顺序：

| 设置 | 行为 |
|---|---|
| `VSDLSS_PERM_SH=8..16` | 固定块 2^k 个 double（15 = 256 KB，16 = 512 KB） |
| `VSDLSS_PERM_SH=auto` | 实测：前 6 次两遍求解交替用 2^15、2^16，各 3 次取中位数（收集+写回），2^16 快 5% 以上才选它，之后固定 |
| 不设置 | 每核 L2 ≥ 1 MB（`sysconf`，否则 `/sys/.../cache`）用 2^16，否则 2^15 |

- 选择按线程数分别进行，与计划一起缓存在因子中；实测只在持有 scratch 锁的求解里进行，并发求解走直接循环，不参与计时。
- 实测期间两个计划同时存在，32M 时多占约 250 MB（每个计划约 8 B/顶点），决定后立即释放落选者。
  内存不足以建第二个计划时直接采用已有的那个。
- `VSDLSS_TRACE=1` 打印决定：`perm block auto, T threads: 2^15 x ms, 2^16 y ms -> 2^k`。
- `test_parallel` 覆盖 2^8、2^12、2^15、2^16、L2 规则和实测（须收敛到单一计划），逐位对比直接循环；
  2^8 在测试矩阵上产生上百个桶和大量跨分量的块。

6M 客户分布、1 线程（本机 L2 2 MB，规则选 16）：2^15、2^16、规则、auto 的收集+写回都是 0.057–0.058 s，
auto 测得 58.0 / 59.2 ms，保留 2^15。这一规模、单线程下两者无差别；32M 多线程下的差别需在目标机器上看
（`VSDLSS_PERM_SH=auto VSDLSS_TRACE=1` 跑一次即可看到决定和两个中位数）。

## 32M：库代码本身（无需分解）

`test/bench_perm_lib.c` 直接 `#include "vsdlss_m3.c"`，构造与电网相同形态的分量布局
（两张网按 52/48 分顶点，另加若干 1–300 顶点的小分量，全局编号为随机双射），
用库自己的 `build_inverse` 建逆映射，然后运行库里的直接循环（`solve_local` 的收集循环、`write_back_inverse`）
和两遍路径（`perm2_gather` / `perm2_writeback`，计划和 scratch 的处理与 `solve_common` 相同）。
每次都逐位检查：收集后 `packed[p] == rhs[vertices[p]]`，写回后 `out == rhs`。
`PERM_TREE=<检出目录>` 可对另一棵树的源码编译，用于改前改后 A/B：

```sh
git worktree add /tmp/old c3fffd0
make -B bench_perm_lib PERM_TREE=/tmp/old && mv bench_perm_lib bench_perm_lib_old
make -B bench_perm_lib
for t in 4 8; do ./bench_perm_lib_old 32000000 $t 8; ./bench_perm_lib 32000000 $t 8; done
VSDLSS_PERM_SH=auto VSDLSS_TRACE=1 ./bench_perm_lib 32000000 8 8
```

本机（1 vCPU、L2 2 MB）32M、1 线程、6 次中位数，ms：

| 布局 | 版本 | 两遍收集 | 两遍写回 | 合计 | 直接循环合计 |
|---|---|---:|---:|---:|---:|
| 102 分量，inverse 32 位 | 改前 c3fffd0 | 407 | 399 | 806 | 472 |
| | 改后，2^15 | 185 | 164 | 349（0.43×） | 484 |
| | 改后，2^16 | 183 | 159 | 343（0.43×） | 475 |
| | 改后，L2 规则（选 2^16） | 178 | 155 | 333（0.41×） | 454 |
| | 改后，auto（测得 353 / 365 ms，选 2^15） | 181 | 159 | 340（0.42×） | 464 |
| 2002 分量，inverse 64 位 | 改前 | 384 | 391 | 775 | 463 |
| | 改后，L2 规则（2^16） | 200 | 155 | 355（0.46×） | 458 |

峰值 RSS：改前 1.47 GB，改后 1.59 GB（桶号数组与填充）。
单线程下改前的两遍法比直接循环还慢（这台机器上），改后快于直接循环约 1.3–1.4×。
256 KB 与 512 KB 在这里只差约 2%，auto 按 5% 门槛保留 2^15，符合设计。
