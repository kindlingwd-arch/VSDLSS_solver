# 远程 main 尾部回代优化空间分析（2026-10-11）

结论：还有明确的算法优化空间。优先研究回代独立依赖图和同线程跨层任务合并，再做按层形状选择线程数。当前证据不能保证在最新 main 上再获得 8 倍回代加速，更不能把层数减少倍数当作耗时减少倍数。

[main 快照的 vsdlss_m3.c](https://github.com/kindlingwd-arch/VSDLSS_solver/blob/85792d29b4fe91c87d8cb16e919666b0d8f578e4/src/vsdlss_m3.c) 的 `relabel_component` 已经使主元向量连续、度数缩为 1 字节；不能再把“改成连续主元”当作尚未实现的收益。`chain_order`（230 行）也已存在，但 `VSDLSS_CHAIN_ORDER=1` 默认关闭。

因此，早期“尾部全部单线程”的描述已不适用于所有当前 main 用例。是否串行取决于有效分层、平均层宽、粒度和分量内部可用线程预算。

例如，假设仍有平均每层 48000 条记录，默认 grain=2048，尾部线程上限约为 23；申请 32 或 64 线程不意味着这段就会使用全部线程。链连续编号会改变尾部形状，需要重新统计。

## 2. 最有价值的剩余算法空间：回代真实依赖

对每条消元记录，回代计算为：

```text
value = rhs_at_pivot / pivot
for j in original_neighbor_order:
    value -= multiplier[j] * x[neighbor[j]]
x[pivot] = value
```

每个主元仅被写一次。两个记录共同读取同一个邻居不构成回代的写冲突；它们只需要等待该邻居的生产者完成。现有 `level_tail` 则会将这种共同触碰也排序，因为前消元对邻居执行写更新，且必须保留这些更新的数值顺序。

诊断在现有 packed tail 上逆序扫描，计算：

```text
depth[core_vertex] = 0
depth[pivot] = 1 + max(depth[eliminated_neighbors])
```

这是同一组回代记录的真实依赖深度，保持每条记录内部的浮点顺序。它不是新的求解实现，也没有测量新的调度器耗时。

| 输入 / 配置 | 尾部记录 | 当前冲突层 | 回代真实依赖深度 | 当前平均层宽 |
|---|---:|---:|---:|---:|
| 已有 400 万节点 far，默认编号 | 3,534,501 | 396 | **90** | 8,925 |
| 可复现 100 万节点 wires，默认编号 | 328,032 | 123 | **31** | 2,666 |
| 同一 wires，链连续编号 | 8,374 | 10 | **3** | 837 |

400 万输入中，尾部占消元记录 90.1474%，当前层宽最小 2、最大 46778。真实依赖的层数比当前少约 77.3%。尾部度数为 2 的记录占 99.9931%；约 50.5% 的邻居边指向已求解核心，余下的尾部依赖平均约 0.99 条/记录。这支持进一步检查链状依赖，但平均值不能代替逐记录的入度直方图。

100 万输入的默认编号真实依赖层数比当前少约 74.8%。这些结构性结果说明有不必要的同步约束；它们**不能证明**回代时间将缩短 74% 或得到 4 倍加速。独立调度若增加记录间接访问、破坏局部性，也可能抵消收益。

## 3. 同一分解上的线程粒度交替测量

100 万 wires，默认编号。每个配置预热 2 次、记录 15 次；grain=2048 与 256 在同一分解中交替执行，向量重置、逐次数值比较均在回代计时之外。

表格范围为两个独立进程各自的中位数范围，不是所有样本合并后的中位数，也不是置信区间。

| 申请线程 | grain=2048 实际尾部线程 | 回代中位数 ms | grain=256 实际尾部线程 | 回代中位数 ms |
|---|---:|---:|---:|---:|
| 4 | 1 | 0.876572–0.907144 | 4 | **0.500745–0.584410** |
| 8 | 1 | 0.920395–1.146164 | 8 | **0.556644–0.800257** |

两个进程中位数的算术平均：4 线程申请时，0.891858 → 0.542578 ms，约减少 **39%**；8 线程申请时约减少 **34%**。4 线程常比 8 线程更有效，不能按线程数线性外推。

但同一输入启用链连续编号后，尾部只有 8374 条记录：

| 申请线程 | grain=2048 / 实际线程 | 回代中位数 ms | grain=256 / 实际线程 | 回代中位数 ms |
|---|---|---:|---|---:|
| 4 | 2048 / 1 | **0.021375–0.021868** | 256 / 3 | 0.133992–0.147428 |
| 8 | 2048 / 1 | **0.022490–0.023270** | 256 / 3 | 0.403559–0.498853 |

强行并行反而慢约 6.5 倍或 19.7 倍。尾部视图仍经过原生产入口及空块段的线程区域，两种粒度均如此；短尾部下线程组切换和同步成本无法忽略。这里的倍数描述微秒级尾部入口，不等于整体求解退化倍数。

**不能直接把全局默认 grain 改成 256。** 更合理的是按尾部规模、各层宽度、线程切换和实测成本选择策略，并保留小尾部串行路径。

## 4. 尾部缩小与全求解耗时的关系

采用当前 main 已有的链连续编号后，100 万 wires 的尾部从 328032 条变成 8374 条，记录数减少约 97.45%，因为更多消元进入并行块。全部消元记录数仍约 98 万；这些计算没有消失。

默认 grain 下，4 线程申请的尾部回代中位数：默认编号 0.959203–1.318955 ms，链连续编号 0.020804–0.021508 ms。两者的完整求解中位数分别为 24.147651–27.609175 ms 和 21.378686–22.265089 ms。8 线程完整求解的范围重叠明显：默认 25.088534–29.115891 ms，链连续编号 24.991238–25.066836 ms。

因此，尾部时间大幅下降不能当作完整 solve 的同比收益。编号同时影响块消元、核心及映射，进程之间还有频率和调度波动，以上不是单个回代内核的因果性能结论。

当前 main 的求解账本显示，这个 100 万输入默认编号、4 线程时，**全部低度回代**只占完整 solve 均值的 7.75%–8.90%。如果其他阶段成本不变，即使消除全部低度回代，完整 solve 也只会减少约 8%–9%；只优化其中尾部的收益更小。这里的百分比不能外推到用户的大规模用例。

账本并行核心路径把部分前后代合并计入 `core_fwd`；报告核心成本时应合计 `core_fwd + core_bwd`，不能把日志中的 `core_bwd=0` 理解为没有核心回代。

## 5. 下一轮开发优先级

1. **回代专用依赖计划。** 前消元仍保留当前数值更新顺序；为回代去掉共同读取邻居产生的额外约束。首先统计真实入度、链长、跨块边和层宽分布，避免只看平均值。构建真实依赖深度可用 O(R+E) 扫描，临时按顶点的 uint32 深度约 4N 字节；调度索引和邻居偏移的常驻成本需要单独核算。
2. **同线程依赖链跨层合并。** 同线程的生产者和消费者按顺序连续执行，只在跨线程依赖处同步。先采用受限的连续块或链任务，避免每条记录一个 OpenMP task / 原子队列。任务合并必须证明图无环，不能任意把记录分组。
3. **按形状选择串行、层并行和链任务。** 小尾部串行；宽层并行；窄层和长链优先合并。用实际线程数、每层最长线程工作量和线程组切换成本建立判据，替代仅凭平均记录数的全段判断。
4. **访存与内核调整。** 合并连续 32 条块、度数专用内核和 SIMD 可作为局部增强，但必须同时测量缓存局部性。平均度数 2 时，现有紧凑记录约 33 字节/条；另有主元向量读写和邻居向量读取。不能把记录字节除以时间当作完整 DRAM 带宽，也不能在没有硬件计数器时宣布“带宽已饱和”。

数值约束：保留每条记录的除法和邻居运算顺序、有限性检查；不用倒数替代除法，不引入 FMA 或 fast-math。独立调度预期可以逐位一致，但需要新路径与当前 main 按每次 RHS 比较后才可确认。链连续编号改变消元顺序，应检查残差和解差，不能要求与默认编号逐位一致。

参考方向：[Park 等，ISC 2014](https://link.springer.com/chapter/10.1007/978-3-319-07518-1_8)研究精简依赖同步；[Efficient Parallel Scheduling for Sparse Triangular Solvers，v2](https://arxiv.org/html/2503.05408v2)研究将同线程依赖工作合并到一次同步之间，并兼顾负载和存储局部性。这些论文支持研究方向，文献速度倍数不是本项目的实测收益。
