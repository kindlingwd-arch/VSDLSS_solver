## 1. 背景：一次求解读了什么

M3 求解一个网（VDD 或 GND）分三段：

1. **前代回放**：按消元顺序处理约 3000 万条低度消元记录。每条记录读主元、乘子和邻居下标，算出主元值 $s_i$，把它推给邻居。
2. **core 求解**：对剩下的 core 结点做超节点三角求解（读两遍 core 因子）。
3. **回代回放**：按相反顺序再处理同一批记录，由邻居的电压恢复每个被消去结点的电压。

消元记录约 2 GB，远大于缓存。求解受内存带宽限制，每步时间约等于"读的字节数 ÷ 实际带宽"。前代、回代各从内存把这 2 GB 读一遍。**如果第二遍能命中缓存，就能少读一遍。**

一次求解内部做不到：回代要等 core 求解完，core 又要等全部前代完成，消去树只有一个根。中间隔着 GB 级的数据，第一遍的记录早被挤出缓存了。融合的想法是换个方向：**把这一步的回代和下一步的前代接起来。**

## 2. 数学原理

### 2.1 后向欧拉的递推

每个时间步解

$$
\underbrace{\Bigl(G+\tfrac{C}{h}\Bigr)}_{A\ (\text{固定})}\,x_{k+1}
=\underbrace{\tfrac{C}{h}\,x_k+I_{k+1}}_{b_{k+1}}
$$

A 在步与步之间不变，只分解一次。接口里记 $C_h=C/h$，$s_{k+1}=I_{k+1}$（电流源及其他与解无关的项）。

### 2.2 关键性质：右端项是局部的

电容接地时，$C_h$ 是对角矩阵：

$$
b_{k+1}[v]=d_v\,x_k[v]+s_{k+1}[v],\qquad d_v=(C_h)_{vv}
$$

**结点 v 下一步的右端项，只依赖它自己这一步的电压**，不需要别的结点。

### 2.3 依赖分析：为什么可以按单元交错

把消元记录分成若干"单元"（第 3 节）。看第 k+1 步前代处理一个单元 U 时需要什么：

1. U 内各结点的 $b_{k+1}$：由 2.2，只需要 U 内结点的 $x_k$；
2. U 内更早的记录推过来的量：在 U 内部按顺序处理即可；
3. 其他单元推给 U 的更新：如果有，必须先到（第 6 节处理）。

而 U 内结点的 $x_k$，正是第 k 步回代处理 U 时算出来的。所以单元 U 的第 k+1 步前代可以执行的条件是：

$$
x_k[U]\ \text{已就绪}\ \land\ I_{k+1}[U]\ \text{已知}\ \land\ U\ \text{的第 } k+1 \text{ 步前代的所有前驱更新已完成}
$$

对角电容只保证第一条可以在单元内部满足；第三条取决于单元之间的消元依赖，以及共享目标上的浮点更新顺序（第 6 节）。U 没有外部前驱时，才能

> 第 k 步回代完 U → 立刻算 U 内结点的 $b_{k+1}$ → 立刻做 U 的第 k+1 步前代，

而其他独立单元此时仍可以在做第 k 步回代。

严格说，对角 $C_h$ 是充分条件：两端电容的两端都在同一个单元里时，等这个单元回代完，也能在单元内算出 $b_{k+1}$。现在的实现对非对角电容更保守，一律当作特殊结点晚做；线上用例没有非对角电容，这一点不影响它。

三件事读的是同一批记录和同一段向量，单元又放得进缓存，后两件几乎不访问内存。

### 2.4 为什么结果逐位不变

融合只改变"不同单元之间"的执行先后，不改变：

- 每条记录的算术（同样的乘除、同样的次序）；
- 每个向量元素受到的运算序列：先被赋值为 $b_{k+1}[v]$，再受块的更新，再受尾部的更新，最后受延后的 core 更新（按消元顺序）。

浮点运算不满足结合律，所以第二条必须严格保持。只要每个元素的运算序列和逐步求解时相同，结果就逐位相同。凡是会打乱这个序列的单元，都推迟到所有回代完成之后再做（"晚做"，第 6 节）。

## 3. 融合的单元

现有的低度消元把记录分成两部分，正好是天然的单元：

| 单元 | 来源 | 性质 |
|---|---|---|
| **块**（块并行段） | 低度消元按块并行：块 b 只消去"邻居全在本块内"的结点 | 记录只读写本块结点，以及本块边界上的尾部或 core 结点；块与块的被消去结点互不重叠 |
| **尾部连通块**（chunk） | 尾部按单窗口调度时，按连通分量切成的块，线上用例平均约 700 条记录、约 20 KB | 连通块之间互不相交，只通过 core 结点联系；对 core 的更新是延后的（进缓冲区，最后按消元顺序补减） |

在消元顺序里，块在前、尾部在后、core 最后。所以：

- 前代：块的更新先于尾部的更新到达同一个结点；
- 回代：顺序相反，尾部先、块后。

单元足够小（约 20 KB），放得进 L2 缓存，这是"第二遍命中缓存"的前提。

## 4. 数据和向量

每个网用四个按打包顺序存放的 n 维向量（每结点 32 字节，6100 万结点共约 2 GB）：

| 向量 | 内容 |
|---|---|
| `x` | 第 k 步的解 $x_k$ |
| `w` | 工作向量：前代时累积右端项；前代结束时，每条记录的主元值 $s_i$ 留在其结点位置上，core 位置上是 core 的右端项 |
| `s` | 这一步的电流源（稀疏登记，每步散布成打包顺序） |
| `d` | $C_h$ 的对角 |

另有 `buf`：尾部对 core 的延后更新，每次更新的乘积（不是单元内已经求和的贡献）写进预先分配的唯一槽位，最后由每个 core 目标的唯一任务按原消元顺序相减。

**x 和 w 必须分开。** 回代第 k 步时，块要读尾部和 core 结点的 $x_k$；而同一时刻，尾部连通块的第 k+1 步前代已经在改写这些位置的 `w`。合用一个向量就会读到下一步的值。

回代从 `w` 读主元值、写入 `x`（`backward_range_tr`），和原地求解时"从 x 读、写回 x"读写的是同一个数，算术完全相同。

## 5. 一次迭代的执行流程

`vsdlss_m3_transient_run` 每次迭代完成第 k 步、准备第 k+1 步。两个网用 `run_components` 并发，各用一半线程。

```
第一次 run 之前（phase_pro）：
    w = d·x0 + s1，做第 1 步前代                      （没有前一步的回代可以融合）

每次迭代：
A  (phase_a + vsdlss_reduce_tr_step_a)
   ① core 求解第 k 步：w[core] 拷到 x[core]，原地求解
      非特殊 core 结点：w[v] = d[v]·x[v] + s[v]         （core 结点的 b_{k+1}，等待累加）
   ② 尾部连通块，并行（dynamic 调度，每个连通块一个任务）：
        a. 回代第 k 步：读 w 中的主元值和邻居的 x，写 x
        b. 本块非特殊结点：w[v] = d[v]·x[v] + s[v]
        c. 不晚做的：立即做第 k+1 步前代（对 core 的更新写进延后缓冲区）
   ③ 块，并行：同 ②（回代 k → 算 b_{k+1} → 不晚做的立即前代 k+1）
回调 (ask)
   把完整的 x_k 交给调用者，调用者给出第 k+1 步 dep 结点的值
B  (phase_b + vsdlss_reduce_tr_step_b)
   ④ 特殊结点的 b_{k+1}（需要别的结点的 x_k，或回调给的值）
   ⑤ 晚做的块、晚做的连通块：做第 k+1 步前代
   ⑥ 按消元顺序，把延后缓冲区里的 core 更新补减到 w[core]
→ 下一次迭代的 ① 用 w[core] 解第 k+1 步
```

几点说明：

- **必须一次调用推进多步才有融合。** 连续调用 `run(1)` 时，每次都只做启动和收尾，没有相邻的两步可以在一次调用里融合。每批的第一遍前代和最后一遍回代都不能跨批复用。
- ② 在 ③ 之前，是回代的方向要求：尾部在消元顺序上更靠后，回代先做尾部；块回代时要读尾部结点的 $x_k$。② 和 ③ 之间有一道屏障（两个 `omp for` 之间的隐式屏障）。
- ② 里每个连通块的前代立即执行。它对 core 的更新不直接减到 `w[core]`，而是写进缓冲区（`forward_range_defer`），到 ⑥ 再按消元顺序补减。这和普通求解的"窗口调度 + core 累加延后"是同一套机制，所以 core 右端项的累加顺序和逐步求解一样。
- 不能融合的分量（第 7 节）在 B 阶段单独解第 k+1 步（`solve_separate`），算术与 `vsdlss_m3_solve_packed_inplace` 相同。
- 每个单元回代完，马上在缓存里算本单元的 $b_{k+1}$。设计里的 P2（"b 在回代时顺手算出"）就是这一步，已经包含在融合路径里。

## 6. 晚做规则：逐位一致的保证

一个单元的第 k+1 步前代，只要满足下面任一条件，就推迟到所有回代完成之后（B 阶段 ⑤）。规则在 `vsdlss_reduce_tr_plan` 里，分解后、create 时算一次。

| 规则 | 适用 | 不晚做会怎样 |
|---|---|---|
| 1. 单元里有**特殊结点**：两端电容的端点、dep 结点 | 块、连通块 | 它们的 $b_{k+1}$ 需要别的结点的 $x_k$（或回调的值），这时还没有 |
| 2. 单元**更新了某个特殊结点** | 块、连通块 | 特殊结点的 $b_{k+1}$ 要在 B 阶段 ④ 才赋值；提前更新就违反了"先赋值、后更新" |
| 3. 连通块的某个结点**被块更新过** | 连通块 | 块的前代在 ③ 才做，在连通块 ② 之后；连通块提前做前代，就读不到块推来的量（数据依赖） |
| 4. 连通块直接更新的某个 core 结点**也被块更新过** | 连通块 | 逐步求解时，这个 core 结点先受块的更新、再受尾部的更新；提前做会颠倒这两者的次序，浮点结果改变 |

规则 3 是数据依赖，违反了结果就错。规则 4 只关乎累加次序，违反了结果仍是对的，但不再逐位一致。实现选择保留逐位一致，以便用"逐步求解"做回归。

### 6.1 形式化的晚做条件

记 $Q$ 为特殊结点，$\mathrm{Touch}_B$ 为被块前代更新的尾部或 core 结点，$V(U)$ 为单元自己被消去的结点，$N(B)$ 为块前代的全部更新目标，$\mathrm{DirectCore}(T)$ 为尾部单元直接更新（不经缓冲区）的 core 目标：

$$
\mathrm{Late}(B)\iff \bigl(V(B)\cup N(B)\bigr)\cap Q\neq\varnothing
$$

$$
\mathrm{Late}(T)\iff V(T)\cap\bigl(Q\cup \mathrm{Touch}_B\bigr)\neq\varnothing\ \lor\ \mathrm{DirectCore}(T)\cap\bigl(Q\cup \mathrm{Touch}_B\bigr)\neq\varnothing
$$

普通电流源结点不是特殊结点：电流源再稠密，也不影响能否融合，只增加每步散布电流源的开销。

对照实验（`test/test_transient.c`）：去掉晚做判定，第 2 步起就和参照不一致；算 b 时漏掉非对角项，有 48 处不一致。

### 6.2 逐位一致的证明

参照算法：用同一个因子，按同一个公式逐步组装 $b_k$，逐次调用 `vsdlss_m3_solve_packed`。

**命题 1：每次回代读到的都是第 k 步的正确输入。** 尾部回代开始前，core 已经解出 $x_k[\text{core}]$。尾部单元的回代只依赖本单元更晚消去的结点和 core，单元内按逆消元顺序执行。尾部阶段结束有屏障，块回代需要的尾部和 core 电压都已就绪。提前做的下一步前代只改 `w`、不改 `x`，也不碰块尚未读取的主元位置。

**命题 2：每个下一步工作元素都先赋值为右端项，再接受更新。** 普通 core 结点在单元任务启动前赋值；普通尾部结点在本单元回代后赋值，块前代开始前所有尾部任务已结束；块内结点在本块回代后赋值，别的块不访问它；特殊结点的所有直接更新者都被标为晚做；对特殊 core 的延后更新只写 `buf`。

**命题 3：下一步前代的真实依赖都满足。** 含被块更新结点的尾部单元晚做，在全部块前代之后执行；能提前做的尾部单元不依赖块的更新，内部按正消元顺序执行；块之间访问的结点集合互不相交。

**命题 4：共享目标上的浮点更新顺序不变。** 每个元素 v 上保持：赋值 $b[v]$ ≺ 块的更新 ≺ 尾部的直接更新或按序提交的延后更新。块之间不竞争同一目标；尾部单元内部保持记录顺序；直接 core 目标只有一个尾部单元更新，若它也被块更新，该尾部单元晚做；延后更新按目标分组，每个目标内按原消元顺序逐项相减。

**对时间步归纳。** 起始的完整前代与参照相同。若第 k 步开始时 `w` 与参照的完整前代结果逐位相同，由命题 1–4：core 求解相同，回代得到相同的 $x_k$，右端项相同，下一步前代的运算序列相同，于是第 k+1 步开始时 `w` 仍逐位相同。

### 6.3 为什么必须保序，以及逐位一致的边界

不能把 `value -= u1; value -= u2;` 改成 `value -= (u1 + u2)`，也不能只靠原子减法：原子操作保证不丢更新，但不保证顺序。双精度下取 $a=p=10^{16}$、$q=1$：

$$
\mathrm{fl}(\mathrm{fl}(a-p)-q)=-1,\qquad \mathrm{fl}(\mathrm{fl}(a-q)-p)=0.
$$

逐位一致还要求浮点执行方式固定：相同的舍入模式、相同的乘加融合（FMA 收缩）规则、相同的 core 数值路径，不重新结合求和、不换归约树。只看 C 源码公式相同不够，构建配置也要由逐位回归测试覆盖。

这个证明针对上面的参照算法，不保证和仿真器原来的组装顺序逐位一致：$(C_v x_v)/h$ 与 $(C_v/h)\,x_v$ 在浮点下可能不同。和仿真器比较用误差阈值。

`VSDLSS_TRACE=1` 时，create 打印晚做统计和原因分项：

```
vsdlss trace: transient fusion: 98 chunks, late 98 (special 0, updated by a block 98, direct core update 0);
blocks late 0 of 3515; blocks updating tail vertices of one chunk 1247, of several 2268
```

## 7. 什么时候融合

### 7.1 结构条件（`vsdlss_reduce_tr_fusable`）

- 打包的低度消元，做了求解序重编号（`VSDLSS_RELABEL`，默认开）；
- 有块并行段，尾部是**单窗口**调度（默认配置）；
- core 连续存放。

不满足的分量（小分量、关闭重编号、按层调度的尾部、多窗口）走不融合的路径，结果一样。

### 7.2 收益条件：自动模式（`VSDLSS_TR_FUSE`）

| 值 | 行为 |
|---|---|
| 1（默认，自动） | 只有晚做单元的记录不超过分量记录总数的一半时才融合 |
| 0 | 关闭 |
| 2 | 总是融合（测试用） |

阈值的道理：晚做的单元在 B 阶段要再从内存读一遍记录做前代，它们得不到融合的好处；同时 A、B 两个阶段多了屏障和调度开销。晚做比例高时，开销会超过收益。实测 ibmpg3t、4 线程：强制融合每步 86 ms，不融合 66 ms。

### 7.3 收益模型

设可融合单元的前代、回代共同读取的记录数据为 $R$ 字节，一次推进 $K$ 步：

$$
\text{不融合}\approx 2KR,\qquad \text{理想融合}\approx (K+1)R,\qquad \text{节省}\ (K-1)R
$$

换成每步时间：设记录从内存读一遍的时间为 $T_r$，晚做记录的比例为 $f$，融合的额外开销（多一组屏障、B 阶段的调度、特殊结点）为 $T_o$，则

$$
\text{每步节省}\approx \frac{K-1}{K}(1-f)\,\phi\,T_r-T_o
$$

$\phi$ 是可融合单元中工作集留得住缓存的比例。线上用例每步回放约 60 ms（前代 32、回代 28），其中记录本身（度数、主元、下标、乘子）约占 2/3，所以 $T_r\approx 20$ ms。即使 $f=0$、$\phi=1$、$K=10$，每步最多省约 18 ms，相对每步 118–135 ms 约 13–15%。这是融合在这个用例上的理论上限；它不减少 core 求解，也不减少"至少读一遍记录"。

约 20 KB 是线上尾部连通块的平均大小，不是每个单元的保证：还要计入 `x`、`w`、`d`、`s` 和 `buf`，大的单元可能超出 L2（Zen 2 每核 512 KiB）。

- 合成网格、尾部主导：$f\approx0$，融合比不融合快 12–24%；
- 线上用例：$f>0.5$，可省的不到一半，还要减去 $T_o$，实测为零。

## 8. 实测

### 8.1 合成网格（本机 4 线程，每步，3 轮各取最快）

| 网格 | 现在的用法 | 新接口，不融合 | 新接口，融合 |
|---|---|---|---|
| grid:150:80 | 54.9 ms | 30.5 ms | 29.5 ms |
| grid:150:80，块 4096 | 53.7 ms | 32.3 ms | **26.7 ms** |
| grid:600:3，块 1024（尾部 200 万条） | 69.6 ms | 46.4 ms | **35.3 ms** |
| grid:150:80，块 1024 | 49.7 ms | 28.6 ms | **25.1 ms** |

- "不融合"相对"现在的用法"已经快 30–45%：省掉了收集和写回，b 在求解器内部并行计算。
- 融合相对不融合，在尾部主导的用例上再快 12–24%，在块大的用例上差别在噪声内。
- 全部和"现在的用法"逐位一致。

### 8.2 IBM 瞬态基准 ibmpg1t–6t

三种做法逐位一致，和官方波形误差 0.56–2.11 mV（后向欧拉对梯形法的 O(h) 差别）。GND 侧 decap 全是两端电容，几乎所有单元都有特殊结点，自动模式判断不融合。

### 8.3 线上 6100 万结点用例（服务器 32 线程，tr_replay_1020_1608）

| 做法 | 自动 | 强制融合 |
|---|---|---|
| tr（不融合） | 144.0 ms | 155.2 ms |
| tr+fuse | 142.2 ms（未融合） | 155.4 ms（两个网都融合） |

全部逐位一致。强制融合与不融合相同，融合没有收益。

## 9. 线上用例为什么没有收益

1. **晚做比例高。** 线上用例有 504 个块、6209 个连通块。10 个块更新了尾部，波及 500–700 个连通块（规则 3）；另有 500–650 个连通块直接更新了块也更新的 core 结点（规则 4）。晚做记录超过一半。
2. **能省的上限本来就小。** 融合最多省一遍读记录（约 30 ms），相对每步约 90–95 ms 的求解本身，再乘以 $(1-f)<0.5$。
3. **合成网格的"降一半"大部分不是融合带来的。** 那里大部分收益来自省掉收集、写回和并行算 b；融合只占 0–24%。线上用例电流源稠密（82% 的结点），散布电流源的开销抵掉了省下的收集和写回；这和能否融合无关（第 6.1 节）。

## 10. 什么电路适合

融合有收益需要同时满足：

- 电容接地（$C_h$ 对角），两端电容和有状态元件少；
- 尾部主导、尾部单窗口调度，块很少碰到尾部；
- 记录读取在每步时间里占比大（core 小）。

满足时，用法：

```c
vsdlss_m3_transient_create(F, Ch, nsrc, src_node, ndep, dep_node, &T);
vsdlss_m3_transient_start(T, x0);
vsdlss_m3_transient_run(T, nsteps, src, cb, ctx);   /* 每步回调给出打包顺序的完整解 */
vsdlss_m3_transient_info(T, &fused, &units, &late); /* 是否融合、单元数、晚做数 */
```

`VSDLSS_TR_FUSE=1`（默认）会自己判断。用 `VSDLSS_TRACE=1` 看晚做统计。

## 11. 还能改进的地方

- **直接 core 更新改为按序延后提交**：消除第 6.1 节 Late(T) 的第二项。每次乘积写进按原消元顺序排列的槽位，最后由每个目标的唯一任务按序相减，仍逐位一致。代价是缓冲区流量增加。它解除不了"块更新尾部结点"这条真依赖。
- **块并入连通块**：trace 显示很多块只更新一个连通块（合成网格 3515 个块中 1247 个）。把这样的块放进那个连通块的任务里先做，规则 3、4 引起的晚做就会消失。代价是块与连通块的调度耦合，负载更不均衡。
- **改变分块，让块少碰尾部**：低度消元分块时避开尾部结点。会影响分解阶段的并行度。
- 这几条都只能把 $(1-f)$ 从不到 0.5 往 1 提，收益上限仍是第 7.3 节的约 18 ms（每步 13–15%）。动手之前先用第 13 节的上限测量判断值不值得。
- **原来"每步减半"的设想实现不了。** 它的收益一半来自省掉收集和写回（实测净收益最多约 10 ms），一半来自融合（上限约 18 ms）；两者都做到最好，每步约 118 → 90 ms（约 −24%）。要真正减半，需要减少求解本身读的字节数或减少时间步数，和融合无关。

## 13. 上限测量（2026-10-20 新增，待服务器数据）

两个测量，都不改变正常路径的结果：

1. **trace 统计**（`VSDLSS_TRACE=1`，create 时打印）：
   - `transient fusion records`：单元总记录数、记录和向量的总字节，晚做记录按原因分项（含特殊结点、含被块更新的结点、直接 core 更新与块冲突；一个单元可能有多个原因）；
   - `transient fusion potential`：能立即融合的记录比例，分三种情形——现在、直接 core 更新按序延后（去掉规则 4）、再把只碰一个连通块的块并入该连通块——每种再按工作集 ≤ 512 KiB / ≤ 4 MiB 过滤；
   - `transient fusion unit footprint`：连通块工作集的中位数、P90、P99、最大值，超过 512 KiB / 4 MiB 的记录占比；块的工作集；只碰一个连通块和碰多个连通块的块数。
2. **上限模式** `VSDLSS_TR_FUSE=3`（只用于计时）：所有单元都立即融合，忽略晚做规则。结果**不正确**（晚做的连通块漏掉块的更新），`bench_tr_replay` 用 `PG_FUSE=3` 时不做逐位检查，只计时。它给出融合在这个用例上能达到的最好时间。`test_transient` 检查它能运行、确实融合、结果有限。

服务器上只跑需要的部分：

```bash
cd <转储目录>
env SKIP_UNIT=1 SKIP_SYNTH=1 SKIP_FUSE2=1 SKIP_SAVE=1 TR_PACKED=0 bash <源码目录>/tools/tr_replay_test.sh <源码目录> 32 10 3
```

第 4 步给出不融合的 tr 和 trace 统计，第 6 步给出上限。判断：

| 上限模式相对 tr（不融合） | 判断 |
|---|---|
| 快 10% 以上 | 值得做：按序延后提交 + 块并入连通块，再测真实收益 |
| 快 5–10% | 只做按序延后提交 |
| 低于 5% | 关闭这个方向：瓶颈在缓存容量或额外开销，不在晚做规则 |
