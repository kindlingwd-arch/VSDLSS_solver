# 尾部回代调度研究与开发参考

本笔记服务于 `85792d2` 之后的开发调研。算法空间与本项目实测见 [main 分析报告](tail-backward-main-analysis-20261011.md)，原始样本和复现入口见 [证据目录](../benchmarks/tail-backward-main-20261011/README.md)。这里没有新的求解器实现，也没有将文献中的加速倍数作为项目承诺。

## 文献阅读入口

| 研究 | 一手来源与阅读范围 | 在本项目中需要回答的问题 |

| Park、Smelyanskiy、Sundaram、Dubey，ISC 2014，*Sparsifying Synchronization for High-Performance Shared-Memory Sparse Triangular Solver* | [出版社 / DOI](https://link.springer.com/chapter/10.1007/978-3-319-07518-1_8)，本轮依据公开摘要；没有将订阅全文标为已读 | 哪些跨任务同步是冗余的？块级点对点等待是否比每层全局屏障便宜？ |
| Böhnlein 等，*Efficient Parallel Scheduling for Sparse Triangular Solvers*，arXiv:2503.05408v2 | [版本入口](https://arxiv.org/abs/2503.05408v2)、[全文 HTML](https://arxiv.org/html/2503.05408v2)，重点读 §2–5、§7.3、§7.7 | 同线程依赖如何跨波前执行？如何兼顾负载、屏障和存储局部性？ |
| Andrew M. Bradley，CSC 2016，*A Hybrid Multithreaded Direct Sparse Triangular Solver* | [SIAM / DOI](https://epubs.siam.org/doi/10.1137/1.9781611974690.ch2)，本轮依据公开摘要 | 不同形状是否应在分层和分块之间选择不同策略？ |

以下文献摘要均为原创概述。没有随 PR 转载论文 PDF 或第三方实现。

### 同步精简：Park 等

论文提出删除冗余任务依赖，降低同步成本；公开摘要报告，12 核 Xeon 上相对传统屏障分层方法加速 1.6 倍。该结果属于论文的算法、矩阵和机器，不能直接套到 VSDLSS。[来源](https://link.springer.com/chapter/10.1007/978-3-319-07518-1_8)

**本项目的推断：**应先区分共同读取邻居造成的额外排序，与真正的生产者→消费者依赖。精简同步边时，只删除有可证明替代路径的约束；用于每条记录实际数值计算的邻居与乘子仍须完整保留。

### 同线程跨层聚合：GrowLocal

GrowLocal 在一次屏障之间优先扩展只能由同一核继续执行的依赖工作，再考虑局部性和负载。论文要求跨核依赖跨越同步步骤，而同核依赖可以留在同一步。Funnel 粗化在多数测试中没有进一步改善求解；调度预处理也需要靠重复求解摊销。论文提供 [OneStopParallel 实现入口](https://github.com/Algebraic-Programming/OneStopParallel)，本 PR 未审计或移植其代码。[来源：§2–5、§7.3、§7.7](https://arxiv.org/html/2503.05408v2)

**本项目的推断：**先评估受限的连续块 / 导线链任务，而非直接照搬通用调度器。额外计划可能破坏当前按前消元层存放的连续访问；屏障减少和局部性收益必须分别测量。

### 按结构混合策略：HTS

Bradley 的公开摘要描述将分层和分块方法结合，以适应更广的稀疏结构；HTS 实现位于 Trilinos。摘要没有提供足够细节来验证某个特定任务聚合或线程阈值，后续实现前需阅读全文或对应源代码。[来源](https://epubs.siam.org/doi/10.1137/1.9781611974690.ch2)

**本项目的推断：**串行、宽层并行、链任务不必共享一个固定策略。现有测量已表明，把全局 grain 调低对大尾部有益，对小尾部可能明显退化。

## 回代依赖与数值约束

前消元向邻居写更新，需要保持各邻居的更新顺序；回代只写自己的主元、读取邻居。共同读取同一个邻居不会引起两个回代记录之间的写冲突。

对当前紧凑重编号布局，尾部主元区间为 `[k0, k0 + count)`，每个主元只恢复一次，核心已经求解完成。回代计划可以仅依据真正的邻居生产者建立边，但需要验证：

1. 所有记录恰好执行一次，没有遗漏和重复。
2. 对每条尾部依赖，消费者使用前生产者已经完成。
3. 核心邻居不需要额外尾部生产者；不能把未完成的块记录当作核心。
4. 每条记录保留原来的除法、邻居顺序、乘法、减法和有限性检查。
5. 不用倒数代替除法，不引入 FMA 或 fast-math；线程之间建立正确的内存可见性。

同线程依赖可以在任务内部逆序执行；跨线程依赖需要屏障或有正确 acquire/release 语义的通知。任务分组必须证明粗化图无环。任意合并不连续记录并不能自动保持这一性质。

## 建议的开发实验顺序

下面是项目侧的候选方案，不是已经批准或实现的调度器。

| 阶段 | 要做的实验 | 必须同时保留的对照 | 决策依据 |
|---|---|---|---|
| A：真实结构 | 统计真实依赖入度 0/1/2/3、链长、层宽分位数、跨块边、度数和记录字节 | 当前冲突层、默认/链编号、实际尾部线程 | 是否值得建立独立回代计划，以及计划内存预算 |
| B：独立回代层 | 保留前消元方案，增加回代专用依赖层；先使用简单调度 | main 同一分解、同一 RHS、标量算术 | 屏障下降是否抵消间接访问成本 |
| C：受限任务合并 | 同线程连续块 / 链跨层执行，只保留必需跨线程同步 | B、main；小尾部串行路径 | 时间、最长线程工作量、局部性、尾延迟 |
| D：自适应选择 | 根据规模、层宽、链结构选择串行 / 层 / 合并任务 | main 默认阈值；1/2/4/8 实际线程及目标服务器线程数 | 大尾部收益与小尾部退化都可解释 |

O(R+E) 的依赖深度扫描只能证明结构空间，不能证明求解速度。若新增常驻的 uint32 记录索引和偏移，每条记录约增加 8 字节；3200 万条记录即约 256 MB（十进制），尚未计入依赖列表和临时构建空间。因此，计划构建耗时、常驻内存、一次求解与多步求解都应报告。

## 验收与计时要求

- **数值**：与 main 同一组消元记录、每次 RHS 比较；覆盖保存 RHS 和原地 RHS、度数 0–3、混合度数、边界块、非有限值和分配失败回退。链连续编号改变消元顺序，需要独立残差 / 解差对照。
- **时间**：预热后交替 A/B，记录逐次墙钟时间、最小值 / 中位数 / 最大值；不把两个进程中位数的平均称为合并样本中位数。
- **阶段**：分别报告尾部、全部回放、完整 solve 和完整仿真步；向量重置和数值比较放在相应计时之外。
- **线程**：在尾部入口独立记录实际线程组，不能用核心或其他分量观测替代；检查亲和性、嵌套预算和双网并发。
- **归因**：记录屏障数、任务数、最长线程工作量、计划字节；有硬件计数器时再分析缓存缺失、除法和实际内存流量。
- **收益**：报告调度构建成本及摊销步数。定义额外计划耗时为 `Tplan`、每步节省为 `ΔT > 0`，至少需要约 `ceil(Tplan / ΔT)` 步收回成本；若 `ΔT <= 0`，不存在有限摊销点。
- **目标**：用户希望回代时间降至原来的 1/8，仍需在生产输入和目标服务器上验收；本次 396→90 / 123→31 是依赖深度结果，不能据此宣称 8 倍加速。

后续若引用外部实现，应先记录准确提交及许可证，再单独审查迁移范围；本参考 PR 仅保存链接、原创分析和项目自身测量资料。
