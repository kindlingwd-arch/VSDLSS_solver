# 瞬态单右端项求解实验（2026-09-24）

按 PR #5（`codex/transient-emir-direct-solve-roadmap-20260924`）的路线，在瞬态工作负载上测量求解瓶颈，并逐项实验。重点是原始编号接口 `vsdlss_m3_solve`。

环境：i7-1260P，WSL2 Ubuntu 20.04，GCC 9.4，笔记本内存带宽在约 4 线程时饱和。

## 基准：`test/bench_transient.c`

- A = G + C/h（对角接地电容 0.5–5 fF，h = 10 ps），只分解一次。
- 每步组装 b_k = i_k + (C/h)·v_{k-1}（8 组脉冲/阶跃/斜坡负载，30% 节点带电流），然后求解一次。
- 同一步分别用打包接口和原始编号接口各解一次，并按 `TR_CHECK` 间隔做逐位比较和后向误差检查。
- 结束时打印最终解的 FNV 哈希，用于跨构建、跨线程数的逐位比对。
- 同时报告低度消元尾巴的依赖层数。

```
./bench_transient [order] [threads] [nrhs] [shuffle] [N d1..d6p]
env: PG_NETS=2 TR_STEPS TR_H TR_CFRAC TR_IFRAC TR_CHECK TR_ALIAS
```

## 基线

| 用例 | 线程 | 打包求解 | 原始编号求解 |
|---|---|---|---|
| 23M 客户双网，AMD | 2 / 4 / 8 | 0.390 / 0.344 / 0.360 s | 0.70 / 0.62 / 0.69 s |
| 16M 双网平均度数 2.5，METIS+MKL | 4 / 8 | 0.515 / 0.492 s | 0.71 / 0.73 s |

分阶段剖析（每个分量）：

- 23M（T=4）：消元回放前代 0.093 s + 回代 0.071 s，与核心三角求解 0.152 s 相当。
- 16M（T=8）：核心 0.35–0.44 s 占大头，回放约 0.04 s + 0.04 s。
- 原始编号接口的收集和写回：编号有序时 0.035 + 0.015 s，编号打乱时 0.095 + 0.055 s。

## 实验结论

| 实验 | 结果 | 处理 |
|---|---|---|
| 消元回放去掉 `saved` 数组 | 23M：0.355 → 0.331 s（T=4），0.360 → 0.329 s（T=8）。16M 原始编号接口：有序编号快 4–6%，打乱编号快 1–2%。逐位一致 | **上线** |
| 低度尾巴分层并行回放 | 尾巴每网约 100 万条记录、5–7 层；回放阶段慢 10–20% | 不上线 |
| 核心前代 DAG 调度（OpenMP task） | 前代 0.079 s，与屏障调度持平 | 不上线 |
| 原始编号接口原地回放（记录下标预翻译为全局编号） | 相对打包接口的耗时比：有序编号 1.14× → 1.13×，打乱编号 1.40× → 2.08× | 不上线 |
| 打包接口原地求解（不做最后拷贝） | 与原始编号接口无关，且会改变失败时的输出约定 | 暂不上线 |

### 为什么 `saved` 可以去掉

顶点 v_i 在记录 i 处被消元后，后续记录不再更新它，核心写回也只触及核心顶点。所以前代结束时 `work[v_i]` 正好等于 `saved[i]`，回代可以直接从同一向量读出。

这样每个消元节点每次求解少写 8 B、少读 8 B。打包约简也不再保留 `saved` 缓冲区（16M 约省 90 MB）。未打包的约简（n > 2^30）仍然使用 `saved`。

### 为什么另外三项没有收益

求解受内存带宽限制，不受依赖或同步限制：
- 串行尾巴本身访存连续、缓存友好；分层版本要额外读索引数组、做分散访存，读的字节反而更多。
- DAG 解决的是线程等屏障，而线程实际上在等内存。
- 原地回放放弃了 BFS 重排带来的局部性：编号有序时收集和写回本来就便宜，编号打乱时整个回放都变成随机访存。

实验代码保存在补丁 `experiments-20260924-full.patch` 中（不入库）。开关：`VSDLSS_TAIL_LAYERS`、`VSDLSS_FWD_DAG`、`VSDLSS_GLOBAL_REPLAY`、`VSDLSS_PACKED_COPY`。

## 验证

- `make test` 通过，含 `OPENMP=0` 串行构建。
- `test_m3` 新增用例：打包约简在 `saved = NULL` 下的前代和回代与带 `saved` 时逐位一致；未打包约简传 NULL 返回 INVALID。
- 16M（METIS+MKL，T=8）与 `origin/main`（`bfd664c`）的最终解哈希一致：有序编号 `316826487654113d`，打乱编号 `6edf138836a1107e`。
- 23M（AMD）在 T=2/4/8 下，与去掉 `saved` 之前的代码哈希一致：`541478587db57050`（在包含同一改动的实验构建上测得）。
