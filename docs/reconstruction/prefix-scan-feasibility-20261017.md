# 前代/回代的仿射前缀扫描：可行性评估（2026-10-17）

讨论的方案：把链式前代 `y_i = a_i y_{i-1} + c_i` 写成二维仿射变换 `(a, c)`，用结合律做并行前缀扫描，把串行深度从 O(n) 降到 O(log n)。数学上等价，但会改变浮点运算顺序。

结论：**在现在的 CPU 求解器上不做。** 依赖深度已经很浅，不是瓶颈；扫描要多付出约 2 倍的运算和访存，结果也不再逐位一致。只有将来做 GPU 版本、并且依赖层里“窄层”的耗时占比显著时，才值得对那一部分使用。

## 1. 求解阶段受访存限制，不受算术量或依赖深度限制

2288 万结点合成双网（`bench_pg_solve` 生成器，AMD），4 核云机器（每核 L2 1 MB，L3 33 MB）：

| 线程 | 机器顺序读带宽 | 核心三角求解有效带宽（L 读两遍） |
|---|---|---|
| 1 | 6.9 GB/s | 7.5 GB/s |
| 4 | 26.4 GB/s | 25.0 GB/s（约 95%） |

核心求解树顶占 L 的 15.5%，前代树顶多花约 4 ms/分量，约占整次求解的 3%。

## 2. 低度消元回放的依赖结构

### 合成网格（2288 万结点）

| 指标 | VDD 网 | GND 网 |
|---|---|---|
| 消元记录 | 1023 万 | 1108 万 |
| 1/2/3 度记录 | 12% / 76% / 12% | 12% / 77% / 11% |
| 数学依赖深度（读之前所有更新完成即可） | 19 | 20 |
| 保持当前逐位顺序的依赖深度 | 628 | 625 |
| 最长的“度 ≤2 消元互相喂值”链 | 18 | 18 |
| 链长 ≤8 的记录占比 | 99.96% | 99.95% |

### 服务器真实数据（6100 万结点双网 EMIR，见 [tail-replay-optimization-20261011](tail-replay-optimization-20261011.md)）

| 指标 | 数值 |
|---|---|
| 尾部记录（3300 万结点分量） | 3214 万条（99.6%） |
| 依赖深度（core 结点不算冲突；backward 只等要读的值） | 340 |
| 依赖深度（共享任何结点都算冲突） | 666 |
| 平均每层可并行的记录 | 约 9.5 万条 |
| 尾部 32 线程 fwd / bwd（窗口调度） | 20.5 / 19.0 ms；1 线程 249 / 241 ms |

真实数据里确实有较长的依赖链（深度 340，是合成网格的 17 倍）。报告指出它们主要不是 2 度导线链，而是电源轨上接着 via 的 3 度结点。

## 3. 为什么扫描在这里没有收益

- **低度消元本身就是树收缩**：消 1 度结点相当于 rake，消 2 度结点相当于 compress（Miller–Reif）。“把一条链合成一个变换”在分解阶段已经完成，回放时的依赖链只有导线段数那么长。
- **关键路径耗时可以忽略**：340 步 × 每条记录 10–100 ns ≈ 3–34 µs，而尾部回放 32 线程实测约 20 ms，相差上千倍。32 线程只到约 12 倍加速，差距来自带宽、NUMA 和负载不均，不来自依赖深度。
- **代价**：扫描把 340 层压到约 9 层，只能省下几十微秒，却要多付出约 2 倍的运算和访存（回放本身受访存限制），结果也不再逐位一致。
- **逐位一致的约束才是“假深度”的来源**：允许改变累加顺序时，合成网格的深度从约 625 降到约 20。如果要放弃逐位一致，按数学依赖直接分层比扫描更划算，而且不增加运算量。主干的窗口调度（PR #46）已经在保持逐位一致的前提下，把尾部做成每遍只同步一次。

## 4. 扩展到 2 亿结点

以下为外推估计（深度增长方式是假设，需实测）：

| 量 | 6100 万（实测） | 2 亿（估算） |
|---|---|---|
| 尾部记录（单个大分量） | 3214 万 | 约 1 亿 |
| 依赖深度 | 340 | 约 620（按 √n）；最坏约 1100（按 n） |
| 关键路径耗时 | 3–34 µs | 6–110 µs |
| 32 线程回放（按带宽线性增长） | 20 ms | 约 65 ms |

工作量和并行度增长得比深度快，扫描在大规模下只会更不重要。2 亿规模下更需要关注的是：

1. **最大连通块的负载不均**：窗口调度要求最大块不超过尾部的 1/64（`VSDLSS_TAIL_WINDOWS=64`）。1 亿条尾部记录时，这个上限约 160 万条，单线程约 13 ms。可以让 K 随线程数增大，或对大块在块内按依赖层再拆分；这种拆分是精确的，结果仍逐位一致。
2. **内存带宽与 NUMA**：各阶段都受带宽限制，双路服务器上要注意物理页落在哪个插槽。
3. **内存容量**：按比例估算，分解峰值约 48 GB，求解时常驻约 18 GB。
4. **索引宽度**：打包消元记录每分量最多 2³⁰ 个结点；两遍重排的 16 位桶号要求 n ≤ 2³¹；32 位逆映射码不够时自动改用 64 位。2 亿都够用。

## 5. GPU 上的适用条件

扫描有效的条件是“每个处理器分到的工作量”和“依赖深度”同一量级（W/p ≈ D）：

- 32–128 核 CPU：W/p ≈ 1 亿 / 128 ≈ 80 万条，D ≈ 1000，相差近千倍，用不上。
- GPU（上万并发线程）：W/p 只有几千条，与 D 同量级。每层的全局同步约 5–10 µs，340 层约 2–3 ms。

即使在 GPU 上也不是必然有用：

1. 层已经很宽（平均约 9.5 万条），按层调度基本能喂饱 GPU，扫描只对记录很少的“窄层”有帮助。
2. GPU 上成熟的做法是层调度或无同步调度（每条记录用计数器等待前驱），不改变运算顺序，能与 CPU 结果逐位一致。
3. 2 亿结点时右端项和解各约 1.6 GB，经 PCIe（约 25 GB/s）单程约 64 ms，比 GPU 回放本身还慢。只有整个瞬态循环都放在 GPU 上才有意义。
4. 显存：分解可留在 CPU，只把因子和消元记录放进 GPU，80 GB 的卡够用。

GPU 版本的判断顺序：先确认整个瞬态循环能否放在 GPU 上；回放先用层调度或无同步调度；再统计窄层的耗时占比，显著时才对这部分使用扫描。
