# NUMA 放置实验（2026-10-19）

服务器：双路 AMD EPYC 7H12（2 × 64 核，256 个逻辑 CPU，2 个 NUMA 结点，每结点约 504 GB），`kernel.numa_balancing = 1`，透明大页 `always`。

用例：6100 万结点双网 EMIR，`transient_driver`（METIS + MKL），32 线程。

工具：`tools/numa_test.sh`（每组 3 步）、`tools/numa_mem.sh`（进程在各结点上的内存）。

## 1. 结果

### 第 1 次运行（机器空闲，负载 0.2–5）

| 组 | 设置 | 每步 warm 中位数 | 最快 | 每步缺页（minor） | 运行期间 NUMA 提示缺页 | 迁移页数 |
|---|---|---|---|---|---|---|
| A | 32 线程分布在两个插槽，内存按首次写入（现状） | **563 ms** | 471 | 约 61 万 | 369 万 | 12.1 万 |
| B | 同 A，`VSDLSS_INTERLEAVE=1`（内存交错分布在两个结点） | **151 ms** | 150 | **约 300** | 9.6 万 | 1.4 万 |
| C | 32 线程只用插槽 0（CPU 0–31），内存在结点 0 | 344 ms | 333 | 约 29 万 | 428 万 | 20.4 万 |
| C2 | 64 线程只用插槽 0（CPU 0–63） | 500 ms | 420 | 约 29 万 | 311 万 | 1.7 万 |

首次求解（冷启动）：A 444 ms，B 225 ms，C 433 ms，C2 461 ms。分解约 30–42 s，峰值内存约 15–16 GB。

### 第 2 次运行（机器有其他负载，负载 6–10；只完成了 A 组）

|---|---|---|---|---|
| A | 367 / 183 / 367 ms，中位数 367 ms | 37 万 / 10 万 / 34 万 | 625 万 | 62.4 万 |

### 内存分布（`numa_mem.sh`）

| 组 | 结点 0 | 结点 1 |
|---|---|---|
| A | 58.3% | 41.7% |
| B | 50% | 50% |

## 2. 分析

1. **交错分布（B）是这个用例上测到的最快结果：每步约 150 ms，比现状（A）快约 3.7 倍。** 即使和机器有负载时的第 2 次 A 组（367 ms）相比也快约 2.4 倍。B 的三步之间波动也最小（150–160 ms）。

2. **A 慢的主要原因是内核的自动 NUMA 平衡，而不是内存集中在一个插槽上。**
   - A 组每步约 61 万次缺页，B 组每步只有约 300 次。自动 NUMA 平衡会周期性地取消进程页面的映射，靠随后的缺页（NUMA 提示缺页）观察访问来源，再决定是否迁移页面。A 组运行期间有 369 万次提示缺页、12 万页迁移。
   - 求解阶段每步都要扫过数 GB 的因子数据，被取消映射的页面一被访问就触发缺页，32 个线程不停地陷入内核，页表更新还会引起跨核的 TLB 刷新。
   - 交错分布给内存设了明确的放置策略，自动平衡不再扫描、迁移这些页面，所以缺页几乎为零。
   - A 组的内存分布是 58% / 42%，并不严重偏向一边，说明"数据集中在一个插槽"不是主因。

3. **单插槽（C、C2）也慢，原因相同。** C 的访问全部是本地的，但每步仍有约 29 万次缺页（自动平衡照样扫描），而且只能用一个插槽的内存带宽。C2 的 64 个线程在一个插槽上争抢带宽，比 C 更慢。

4. **结论：每步的时间对缺页次数非常敏感。** 以第 1 次运行为例：每步缺页 61 万 → 563 ms，29 万 → 344 ms，约 300 → 151 ms。

## 3. 是否值得做

| 做法 | 收益 | 代价 | 结论 |
|---|---|---|---|
| 运行时加 `VSDLSS_INTERLEAVE=1`（或 `numactl --interleave=all`） | 每步 563 → 151 ms | 无，不用改代码 | **立即采用** |
| 在求解器库内部，对大块内存自动设置交错策略（`mbind`） | 和上一行相同；调用方（包括你们的仿真器）不需要再设环境变量 | 小：只改大块内存的分配函数 | **值得做**：仿真器如果直接链接库、没有调用交错，就拿不到这个收益 |
| 关闭自动 NUMA 平衡（`sysctl kernel.numa_balancing=0`） | 用来验证诊断：A 组应接近 B 组 | 需要 root，影响整台机器 | 建议做一次验证，不作为正式方案 |
| 按使用者放置（VDD 数据绑定到运行 VDD 的插槽，GND 同理） | 在 B 的基础上把约一半的远程访问变成本地访问，可能再快一些，幅度未知 | 中：需要诊断各数组的位置并调整首次写入或 `mbind` | 等库内交错做完后，再作为下一步实验 |

注意：以前的性能记录（例如每步约 165 ms）是在不同条件下测的；这次 A 组 563 ms 偏慢，与当时的机器负载和自动平衡的扫描时机有关。不同次运行之间的比较，以同一次 `numa_test.sh` 内的 A/B 对比为准。

## 4. 下一步

1. 生产运行立即加上 `VSDLSS_INTERLEAVE=1`。
2. （可选，需要 root）关闭自动 NUMA 平衡后再跑一次 A 组，确认缺页是主因：
   `sudo sysctl kernel.numa_balancing=0`，测完恢复为 1。
3. 已实现，待服务器验证：
   - **库内自动交错**（`VSDLSS_NUMA_INTERLEAVE`，默认开启，`0` 关闭）：在多结点机器上，库的大块分配函数和 core 面板分配在页面被写入前设置交错策略；M3 分解结束时，把求解要反复读取的所有大数组（消元记录、core 面板和下标、映射表、求解工作向量）交错一次，已放置的页面会迁移。
   - **按使用者放置**（`VSDLSS_NUMA_PLACE=1`，默认关闭）：第一次求解时，由求解某个网的线程查询自己所在的结点，把这个网独有的数组迁移到该结点（`MPOL_PREFERRED`）；两个网共用的数组保持交错。需要绑核（`OMP_PROC_BIND=spread`、`OMP_PLACES=cores`）才有意义。迁移是一次性开销，计入第一次求解。
   - 两者都只改变内存放在哪里，结果逐位不变（`test_m3` 的 `test_numa_interleave`）。
4. 服务器上一次对比五种设置：

   ```bash
   bash <源码目录>/tools/ab_test.sh <源码目录> 32 5 3 \
       "VSDLSS_NUMA_INTERLEAVE=0" "" "VSDLSS_INTERLEAVE=1" "VSDLSS_NUMA_PLACE=1" \
       "VSDLSS_INTERLEAVE=1 VSDLSS_NUMA_PLACE=1"
   ```

   依次是：旧行为（首次写入）、库内交错、整个进程交错、库内交错加按使用者放置、整个进程交错加按使用者放置。最后一种里，进程级交错覆盖调用方的右端项和解等所有内存，各网独有的数组再单独放到各自的结点上（给一段内存单独设的策略优先于进程级策略）。

## 5. 库内交错与按使用者放置的服务器实测（ab_test_1019_1231）

`tools/ab_test.sh`，32 线程，每组 5 步，3 轮轮换；这次只跑了前四组（c5 待测）。四组所有步的解 hash 相同（`3b2d5f296982a0ae`），结果逐位一致。

| 组 | 设置 | 各轮中位数（ms） | 中位数的中位数 | 相对 c1 | 最快 |
|---|---|---|---|---|---|
| c1 | `VSDLSS_NUMA_INTERLEAVE=0`（旧行为） | 748 / 335 / 278 | 335.0 | — | 192.7 |
| c2 | 默认（库内交错） | 269 / 165 / 213 | 213.5 | −36% | 164.7 |
| c3 | `VSDLSS_INTERLEAVE=1`（整个进程交错） | 182 / 170 / 158 | 170.5 | −49% | 147.0 |
| c4 | `VSDLSS_NUMA_PLACE=1`（库内交错 + 按使用者放置） | 164 / 171 / 150 | **163.9** | **−51%** | **145.3** |

各阶段 trace 中位数（ms）：

| 组 | 收集 | 前代回放 | core | 回代回放 | 写回 | 合计 |
|---|---|---|---|---|---|---|
| c1 | 103 | 148 | 21 | 44 | 29 | 374 |
| c2 | 33 | 44 | 27 | 33 | 29 | 188 |
| c3 | 32 | 39 | 25 | 36 | 27 | 173 |
| c4 | 32 | **34** | **19** | **28** | 28 | **144** |

分析：

1. **库内交错有效**：不设任何环境变量（c2）就比旧行为快约 1/3，收集和前代回放的大幅下降（103 → 33、148 → 44）与第 1 节"避开自动 NUMA 平衡缺页"的结论一致。
2. **c2 仍比 c3 慢、波动大**（269 / 165 / 213）：库只管自己的大数组，调用方的右端项、解向量以及 driver 自己的其他内存仍是首次写入，照样被自动平衡扫描。c2 和 c3 的阶段时间接近，差别主要在 trace 之外和轮间波动。仿真器直接调库时，同样建议仍加 `VSDLSS_INTERLEAVE=1` 或 `numactl --interleave=all`，或者对自己的大向量调 `mbind`。
3. **按使用者放置（c4）最快且最稳**：前代回放、core、回代回放分别比 c3 少 5、6、8 ms，每步合计约少 20–30 ms（trace 173 → 144 ms）。这三段读的正是各网独有的数组（消元记录、core 面板），放到本地后不再走跨插槽链路；收集、写回读写两网共用的向量，没有变化。迁移是第一次求解时的一次性开销。
4. 每步的总时间（墙钟）里 c3 与 c4 只差约 4%（170 → 164 ms），比 trace 的差距小，说明还有 trace 之外的开销（driver 组装右端项等）与轮间噪声；需要 c5 和更多轮次确认。

结论：按使用者放置值得保留；c5（整个进程交错 + 按使用者放置）预计同时拿到 c3 的稳定和 c4 的本地访问，是生产运行的候选设置。c5 测完后再决定 `VSDLSS_NUMA_PLACE` 是否默认开启。
